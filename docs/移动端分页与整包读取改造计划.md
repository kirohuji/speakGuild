# 移动端分页与整包读取改造计划

更新日期：2026-11-06  
关联排查：[移动端分页与整包读取问题.md](./移动端分页与整包读取问题.md)

## 1. 结论与决策

问题文档的判断基本准确：当前最影响体感的不是 React 列表渲染，也不是 `PrepPager` 本身，而是页面展示第一批数据前，先从 `downloaded_unit_details` 读取并 `JSON.parse` 整个学习包或整个话题。数组随后再 `slice`，只能减少页面上显示的条数，不能减少 SQLite I/O、JSON 反序列化和内存占用。

本次改造采用以下决策：

1. **先解决整包读取，再扩大分页范围。** 如果只把 `slice` 改成 `LIMIT / OFFSET`，但列表数据仍来自整包 JSON，首屏不会变快。
2. **复用现有内容索引表，不重建一套重复数据。** `offline_vocabularies`、`offline_chunks`、`offline_patterns`、`offline_content_refs` 已经在安装学习包时生成，缺少的是稳定顺序、组合过滤和分页读取能力。
3. **大字段只存一份，读取时各取所需。** 学习计划和详情首屏只读小摘要；单词、句块、句型按页读现有索引。教学文档、练习流水线、场景、Ink 各自单独存放，打开哪一项就只读那一项。不再把它们复制进新的文档表、运行时表，也不再写进聚合整包行。
4. **不是所有内存分页都要数据库化。** 数据量有明确小上限、且已经随当前业务对象加载的列表可以保留 `slice`。优先改无上限、持续增长或会触发整表/整包解析的入口。
5. **离线包版本仍是内容真相源。** 改造不能退回在线接口拼装内容，也不能让服务端新版本内容混入用户已安装的旧包。

## 2. 范围和非目标

### 本期范围

- 学习包详情首屏与单词、句块、句型、话题列表。
- 练习话题准备页；点击开始后才读取的练习流水线；打开时才读取的教学文档。
- 学习计划、今日任务选包、设置当前练习包时的本地包统计与任务元数据。
- 个人页练习记录、学习库收藏等会整表读取的增长型列表。
- `getChunk`、`searchChunks`、`searchSentencePatterns` 未命中索引时扫描全部整包的兜底路径。
- Native SQLite 与 Web SQLite 两个后端保持同一行为。

### 暂不强制改造

- 今日任务中已生成的 `plan.topicStats`：这是一次计划的有界快照，不是数据库查询结果。
- 今日记录抽屉中调用方已传入且数量受日期限制的 `records`。
- 剧本中心中规模有明确业务上限的章节列表。发布记录如果会持续增长，应单独接后端或本地数据库分页。
- 通知、学习商店等已经按后端页读取的列表。
- Virtuoso 虚拟滚动策略；它解决 DOM 数量，不解决数据读取，本期不把它当作数据库分页的替代品。

## 3. 目标架构

### 3.1 一份数据，按用途读取

当前体积大，是因为同一份内容被存了多遍：

- 聚合行 `downloaded_unit_details/{unitId}` 把每个话题的教学文档、练习流水线、知识点再拼进去一次。
- 每个 `topic:{id}` 的 `data` 里同时放着教学文档、流水线、该话题的知识点，以及复制进来的整包 `scene`。打开文档或开始练习都是 `SELECT *` 后整段 `JSON.parse`。
- 知识点正文已经在 `offline_vocabularies`、`offline_chunks`、`offline_patterns`。
- Ink 已经在 `ink_scripts`。

如果再新增 `offline_topic_documents`、`offline_topic_runtime`，又和旧行并存，文档和流水线会再复制一遍。本期不建这两张表。

大字段从合并 JSON 里拆出来，每种只留一行，用现有表的主键区分。`localDb.get(id)` 本来就只读一行并解析这一行，正好符合各取所需。现有实现一律 `SELECT *`，所以不能把文档和流水线放在同一行的不同列里指望不传另一列；原生桥会把整行带回来。

| 主键 | 这一行里只有 | 谁来读 |
|---|---|---|
| `unit:{unitId}:summary` | 包卡片：标题、封面、模式、四项计数、`hasTeachingTopics`、`projectionVersion` | 学习计划、详情外壳 |
| `unit:{unitId}:scene` | 一份场景。不复制进每个话题 | 练习或阅读真正需要场景时 |
| `topic:{topicId}:card` | 话题卡片：标题、难度、排序、计数、`hasTeachingDocument`、`practiceItemIds` | 话题列表、今日任务、进度计算 |
| `topic:{topicId}:teaching` | 教学 Markdown，以及该模式真正要展示的阅读/写作/听力正文 | 打开教学文档或对应模式时 |
| `topic:{topicId}:pipeline` | 练习流水线 | 点击开始练习时 |
| `ink_scripts` 现有行 | Ink | 进入 Ink 时 |

`practiceItemIds` 是当前流水线展开后的练习项 id 集合，不是流水线正文。进度是它和 `daily_practice_items` 里 `bestScoreRank >= 2` 的交集；只存一个总数不够，因为卸载后进度记录还在。这个集合很小，放在卡片行里，学习计划就不必打开流水线。

`hasTeachingDocument` 同样放在卡片行。今日任务只判断有没有文档，不再为了一个布尔值解析整题。

列表只能查卡片行和包摘要行。教学文档行、流水线行、场景行都带 `unit_id` 以便卸载时按包删除，但列表查询必须再加行类型条件（`row_kind = 'card'` 或主键后缀）。不能用现在的 `findByIndex('unit_id')`，否则会把该包每一行大字段都解析出来。`row_kind` 要显式 `ALTER TABLE` 加列，`CREATE TABLE IF NOT EXISTS` 不会给已有表补列。

#### A. 列表继续用现有索引

不把单词、句块、句型再写进话题行或包摘要。扩展现有 `offline_content_refs`：

- 增加 `sort_order INTEGER NOT NULL DEFAULT 0`
- 查询索引增加 `(pack_id, content_kind, sort_order, content_id)`
- 查询索引增加 `(topic_id, content_kind, sort_order, content_id)`

安装时按原数组顺序写入 `sortOrder`。同一知识点出现在多个话题时，包级列表按 `content_id` 去重，顺序取首次出现。这一步不是单表 `listPage` 能表达的，用专用查询：引用表上 `GROUP BY content_id`、`ORDER BY MIN(sort_order), content_id`、`LIMIT/OFFSET`，再按这一页的 id 回表取正文。

#### B. 停止写入聚合整包行

新安装不再写 `downloaded_unit_details/{unitId}` 这份聚合视图，也不再把知识点、场景、教学文档、流水线合并进同一个 `topic:{id}`。兼容期里，这张表的旧行只作为迁移来源。迁移完成后删除该包的旧聚合行和旧话题行，避免新旧两份同时占空间。

### 3.2 仓储接口

页面不得直接拼 SQL，也不直接依赖表结构。建议新增以下仓储接口：

```ts
type PageRequest = { page: number; pageSize: number }
type PageResult<T> = { list: T[]; total: number; page: number; pageSize: number }

getInstalledUnitSummary(unitId: string): Promise<OfflineUnitSummary | null>
listUnitTopics(unitId: string, request: PageRequest): Promise<PageResult<TopicSummary>>
listUnitContent(unitId: string, kind: ContentKind, request: PageRequest): Promise<PageResult<ContentItem>>
listTopicContent(topicId: string, kind: ContentKind, request: PageRequest): Promise<PageResult<ContentItem>>
getTopicDocument(topicId: string): Promise<TopicDocument | null>
getTopicRuntime(topicId: string): Promise<TopicRuntime | null>
```

`getTopicDocument` 只读 `topic:{id}:teaching`，`getTopicRuntime` 只读 `topic:{id}:pipeline`。两个方法不能回退到读取对方那一行，也不能回退到旧的合并话题行。对无限滚动列表可以在仓储内部使用游标；页面层仍只消费统一的 `list / total / hasMore` 结果。固定页码页面可使用 `LIMIT / OFFSET`。

### 3.3 SQLite 基础能力

当前 `ILocalDb` 只有 `list`、单索引全量查找和全表 `count`，无法表达有界组合查询。新增安全的分页查询能力，不向业务层暴露任意 SQL：

```ts
type IndexedFilter = { column: string; value: string | number | null }
type PageQuery = {
  filters?: IndexedFilter[]
  orderBy?: { column: string; direction: 'asc' | 'desc' }[]
  limit: number
  offset?: number
}

listPage<T>(table: TableName, query: PageQuery): Promise<T[]>
countWhere(table: TableName, filters: IndexedFilter[]): Promise<number>
```

所有过滤列和排序列必须在 `COLUMN_EXTRACTORS`/允许列清单中声明，继续使用参数绑定；`limit` 和 `offset` 需要设置合法范围。Native 和 Web 实现共用 `sqlite-json-store.ts`，并补齐 SQL 生成单测。

`listPage` 只服务单表、不需要去重的列表，例如练习记录、学习库、话题卡片。包内知识点分页走 3.1 的专用查询，不要用 `listPage` 假装能做 `GROUP BY`。教学文档和流水线不用分页查询，按主键 `get` 一行。

涉及文件：

2. 给 `downloaded_unit_details` 增加 `row_kind`，列表索引是 `(unit_id, row_kind, sort_order)`。为 `offline_content_refs` 写入 `sortOrder`，并建立 pack/topic + kind + order 的组合索引。
3. 投影在内存里的 `unitDetail/topicDetails` 上一次生成，不要为了建投影再从 SQLite 读回整包。知识点正文只进现有三张内容表和引用表。

涉及文件：

- `apps/frontend/src/features/learning/pages/learning-unit-page.tsx`

任务：

1. 学习包详情先读 `unit:{id}:summary`。当前 Tab 只读第一页知识点或话题卡片，切 Tab 或翻页再查下一页。
2. 话题列表只读 `topic:{id}:card`。不读教学文档行、流水线行，也不带知识点数组。
3. 练习准备页读当前话题卡片和三个知识点的第一页。点击「开始练习」才读 `topic:{id}:pipeline`。
4. 打开教学文档只读 `topic:{id}:teaching`。写作、阅读、听力进入时只读当前话题那一份正文，不先取完整 UnitDetail，也不顺带读流水线。
5. 学习计划和今日任务读包摘要与话题卡片。完成度用卡片上的 `practiceItemIds` 和本地练习记录求交，不打开流水线。
6. 页面分开表示「摘要加载」「列表页加载」「文档加载」「流水线加载」。已经能展示的内容不被另一个大字段的读取挡住。

### 阶段 4：迁移旧包并移除全表兜底

任务：

1. 在 `downloaded_packs` 记录 `projectionVersion`。旧包首次访问时进入兼容路径，并调度一次后台投影构建。
2. 迁移每个包最多解析旧聚合行和旧话题行一次。成功后写入版本，并删除该包的旧聚合行和旧合并话题行，避免新旧两份并存。失败时保留旧路径和可重试状态，不能让已下载内容失效。
3. `getChunk`、`searchChunks`、`searchSentencePatterns` 未命中专用表时，不再 `list('downloaded_unit_details')`。旧包应先触发该包投影修复；无法确认所属包时返回明确的索引缺失状态。
4. 新安装从本阶段开始就不再写聚合整包行。确认迁移覆盖率后，再删除兼容读取。

验收：正常业务路径中不存在 `localDb.list('downloaded_unit_details')`；旧包可用、可恢复、可卸载，迁移中断后下次启动能够继续。

## 5. 优先级

| 优先级 | 问题 | 理由 |
|---|---|---|
| P0 | 学习计划逐包解析整行 | 包越多越慢，属于乘法放大；且返回页面会重复发生 |
| P0 | 学习包详情、话题准备页整包/整话题解析 | 直接阻塞用户看到第一屏，是当前最明显体感问题 |
| P0 | 内容搜索回退扫描全部 `downloaded_unit_details` | 最坏情况会一次解析所有已下载包，应彻底移除 |
| P1 | 练习记录整表读取后切页 | 数据持续增长，改造边界清晰，适合作为分页基础能力的首个落点 |
| P1 | 学习库两表全量读取 | 数据会增长，已有真实索引列可复用 |
| P2 | 今日任务、今日记录的有界数组 `slice` | 当前不是首屏整包解析的主要来源，收益较低 |
| P2 | 剧本中心内存分页 | 需要按各数据源规模分别判断，不能一概改成本地 SQLite 分页 |

## 6. 数据迁移与兼容策略

当前 schema 说明偏向“开发期不兼容时重置本地缓存”，但生产环境的已下载学习包不能只靠清库升级。新表优先于给旧表追加必需列，因为现有 `CREATE TABLE IF NOT EXISTS` 不会给已存在表自动增加列。

建议：

1. 大字段继续放在 `downloaded_unit_details`，用新主键区分，不新建文档表和运行时表。`row_kind`、`sort_order` 用可重复的 `ALTER TABLE` 补上。
2. `offline_content_refs.sort_order` 同样显式加列；也可以建 v2 引用表，降低升级风险。
3. 旧包投影采用“按包惰性迁移 + 空闲时后台预热”，不在应用启动时同时解析所有包。
4. 迁移写入临时版本或以 pack 状态为边界，全部成功后再提交 `projectionVersion`，避免半成品被业务读取。
5. 保留校验器：摘要计数、引用数、话题数与 manifest/旧聚合结果不一致时，不切换新读模型并记录诊断信息。

## 7. 测试计划

### 单元测试

- 分页 SQL 的过滤、排序、边界、参数绑定与允许列校验。
- 相同排序值时的稳定分页。
- 安装后每个话题只有一行教学文档、一行流水线；聚合整包行不存在。
- 读取文档不会读到流水线字节，读取流水线不会读到文档字节。
- 摘要与引用投影生成，含重复知识点去重和原顺序保持。
- 练习项目 ID、教学型/活动型/小说型包的计数与旧实现一致。
- 旧包迁移可重入、失败可重试。

### 集成测试

- 安装、更新、取消安装、安装失败、卸载均不留下孤儿投影。
- Web SQLite 与 Native SQLite 返回相同页、相同总数和相同顺序。
- 离线冷启动进入学习计划、详情、话题准备、开始练习完整可用。
- 更新包后，被移除话题的卡片、文档、流水线都不再残留。

### 页面回归

- 每个 Tab 的页码、总数、返回后位置、空态和错误重试。
- 快速切 Tab、快速翻页时旧请求不能覆盖新请求。
- 点击开始时 runtime 尚未加载，需要有局部 loading 且防止重复启动。
- 低内存设备前后台切换后能恢复，不依赖易失的 Zustand 全量详情缓存。

## 8. 性能验收标准

先以阶段 0 的真实设备基线为准，最终至少满足：

1. 学习计划首屏的 SQLite 读取量不随每个包的完整内容大小增长，只随包数量读取小摘要。
2. 学习包详情首屏最多读取一个 unit summary、一个 topic/content 总数查询和当前列表第一页。
3. 话题准备页最多读取一个话题卡片和各可见 Tab 的第一页。未开始练习前不读取流水线行；未打开文档前不读取教学文档行。打开其中一项时，另一次查询的返回字节里不含另一项。
4. 翻一页时反序列化的业务行数不超过 `pageSize` 加少量引用行，不解析整表或整包。
5. 大包冷启动的“可见首屏”耗时相对基线降低至少 60%；由大 JSON 解析造成的主线程长任务（50 ms 以上）在关键入口消失。
6. 页面切走再回来不依赖重新解析整包；即使内存 store 已释放，也只从轻量投影恢复。

## 9. 建议的提交拆分

1. `perf(offline): add bounded SQLite page queries and metrics`
2. `refactor(records): paginate practice history and notebook queries`
3. `feat(offline): store topic documents and pipelines as separate rows`
4. `refactor(learning): load unit tabs and topic prep on demand`
5. `refactor(progress): calculate plan state from pack summaries`
6. `migration(offline): backfill projections for installed legacy packs`
7. `cleanup(offline): remove downloaded-unit full-scan fallbacks`

每个提交都应能独立回滚；在阶段 3 完成前保留旧读取路径作为 feature flag 回退，待真实设备数据验证后再默认开启新路径。

## 10. 完成定义

以下条件全部满足才算完成，而不是仅把 UI 上的 `slice` 换掉：

- 关键页面首屏不再读取或解析整包 JSON。打开教学文档和开始练习各只解析自己那一行。
- 增长型本地列表使用有界 SQL 查询。
- 安装、更新、卸载、旧包迁移形成闭环。
- 页面结果、顺序、进度计算与当前业务规则一致。
- Native/Web 自动化测试通过，并有至少一台 Android 和一台 iOS 真机性能对比结果。
- 兼容期开关、诊断日志和回滚方式已记录，确认稳定后才能移除旧聚合读路径。
