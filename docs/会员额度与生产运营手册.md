## 1. 核心结论

- **一个会员权益** `pro_member`，两个自动续订商品（月 19 元 / 年 198 元），后端 `user_membership` 为唯一判权来源，RevenueCat webhook 同步 Apple 订阅状态。
- **免费用户额度**：AI 对话判定 5 次/天、AI 汇总分析 1 次/天（`system_config` 可调），额度耗尽可积分兑换或开通会员。
- **会员 = 无限 AI 额度 + 完整内容 + 持续进步服务**；会员页主张从"卖功能"转向"卖持续进步"。
- 当前判断：产品具备进入 TestFlight 和小规模真实用户测试的基础，支付验收、生产监控、转化数据与 7 天进步闭环补齐前不建议大规模公开投放。

## 2. 会员体系

### 2.1 权益对比

| 权益 | 免费用户 | 会员 |
|------|----------|------|
| AI 对话判定 | 5 次/天（可配置） | 不限次数 |
| AI 汇总分析 | 1 次/天（可配置） | 不限次数 |
| 额度耗尽 | 10 积分兑换 1 次 / 开通会员 | 不需要 |
| 学习计划单元 | 基础内容 | 全部解锁 |
| 表达库容量 | 20 条 | 不限 |
| 剧情内容 | 体验部分 | 全部解锁 |
| 邀请好友 | +5 天会员 +100 积分 | +5 天会员 +100 积分 |
| 被邀请奖励 | +50 积分 | +50 积分 |
| 新用户福利 | 前 N 名注册 +5 天试用 | 前 N 名注册 +5 天试用 |

### 2.2 会员计划（后端 MembershipPlan）

```text
name: 漫语町会员
level: standard
price: 1900            # 月付 19 元（分）
yearlyPrice: 19800     # 年付 198 元（分）
durationDays: 30
revenueCatEntitlementId: pro_member
```

- 后端只保留一个会员计划；`price` 月付、`yearlyPrice` 年付（Web 展示与订单用）。
- iOS App 内实际价格以 App Store Connect 为准，前端不硬编码金额。
- `level` 支持 `standard` / `advanced`（均无限 AI 配额，代码中 `QUOTAS` 为 `-1`）。

### 2.3 判权逻辑（AiQuotaService / MembershipService）

```text
请求 AI 服务
  → 管理员（role=admin）：直接放行
  → 会员（status=active 且 expiredAt > now）：无限放行
  → 免费用户：查 AiUsageDaily 今日用量
      → 未达配额：扣减（increment）并放行
      → 已达配额：返回 403 + canExchange 提示（积分兑换 / 会员价格）
```

- 会员赠送天数（邀请/试用）按 `expiredAt` 叠加：`max(expiredAt, now) + days`。
- 状态同步来源：RevenueCat webhook（iOS）、支付宝/微信回调（Web）、mock 确认（非生产）。

## 3. 额度体系（获取 → 消耗 → 恢复闭环）

> **现状**：代码中"消耗点"已存在（4 个 AI 接口 + 积分兑换），但文档未成体系，运营上无法解释"额度从哪来、用到哪、怎么补"。本节定义完整闭环，作为后续开发与运营的统一口径。

### 3.1 额度模型

| 概念 | 说明 | 实现 |
|------|------|------|
| AI 次数额度 | 免费用户每日可用 AI 调用次数，分两类 | `AiUsageDaily.dialogue` / `.summary` |
| 积分 | 跨日累计的通用激励资产，可兑换 AI 次数或订单抵扣 | `User.points` + `PointTransaction` 流水 |
| 会员额度 | 无限（`-1`） | `QUOTAS` + 会员状态 |
| token 成本 | 每日 AI token 消耗量（成本核算） | `AiUsageDaily.tokens`（`recordTokens` 累计） |

`AiUsageDaily`（按 `[userId, date]` 唯一，每日 0 点自然重置）：

```prisma
model AiUsageDaily {
  id       String   @id @default(cuid())
  userId   String
  date     DateTime @db.Date
  dialogue Int      @default(0) // 对话判定次数
  summary  Int      @default(0) // 汇总/分析次数
  tokens   Int      @default(0) // 总 token 消耗量
  @@unique([userId, date])
  @@map("ai_usage_daily")
}
```

### 3.2 额度消耗点（已接入代码，共 4 个 AI 入口）

| 消耗类型 | 接口 | 位置 |
|----------|------|------|
| `dialogue`（对话判定） | `POST /practice-ai/dialogue/judge` | `judgeDialogueTurn` |
| `dialogue`（场景角色扮演轮次） | `POST /practice-ai/scene-roleplay/turn` | `sceneRoleplayTurn` |
| `dialogue`（知识点训练判定） | `POST /practice-ai/warmup/judge` | `judgeWarmupTurn` |
| `summary`（会话汇总分析） | `POST /practice-ai/sessions/:sessionId/analyze` | `analyzePracticeSession` |

> **重要**：TTS 语音合成与 STT 语音识别**不消耗** AI 次数（不在 `checkAndDeduct` 覆盖范围），其成本由 token/调用量单独核算。

### 3.3 额度获取渠道（免费用户）

| 渠道 | 频率 | 数值 | 说明 |
|------|------|------|------|
| 每日基础配额 | 每日自动 | `free_ai_corrections`（默认 5）/ `free_ai_summaries`（默认 1） | `system_config` 后台可调，0 点重置 |
| 每日签到 | 每日 1 次 | 10 + min(连续天数-1, 5) 积分 | 连续打卡加成上限 +5 |
| 邀请好友注册 | 每次 | 邀请人 +100 积分、+5 天会员；被邀请人 +50 积分 | 邀请天数走 `invite_trial_days` 配置 |
| 积分兑换 AI 次数 | 随时 | 10 积分 → 1 次（dialogue/summary 均可） | `exchangeByPoints`，通过扣积分把今日用量 -1 实现追加 |

**待补齐（建议二期）**：

| 渠道 | 设计 | 目的 |
|------|------|------|
| 完成任务奖励 | 完成今日任务 / 完整话题练习 → 少量积分或 1 次 dialogue | 让"练得多"直接转化为"练得起"，避免免费用户过早撞墙 |
| 连续打卡里程碑 | 7/14/30 天额外积分包 | 强化习惯养成 |
| 首练奖励 | 首次完成 AI 对话 → 送积分 | 激活新用户 |

### 3.4 额度恢复与降级

- **每日恢复**：`AiUsageDaily` 按日唯一，新的一天自然重置。
- **即时恢复**：积分兑换成功后当次额度立即生效。
- **升级**：开通会员后即时无限（判权每次实时查询，无需刷新数据）。
- **降级**：会员过期后回到免费配额，历史 `AiUsageDaily` 保留（成本与行为数据），不删除。

### 3.5 额度提示与前端行为

- 接口 403 时返回 `{ message, canExchange, exchangeCost }`，前端展示：
  - 免费用户额度用完 → 提示"今日对话判定额度已用完（5 次/天），10 积分可换 1 次，或开通会员无限畅练"，提供「积分兑换」「开通会员」两个动作。
- 配额状态接口 `GET /practice-ai/quota/status`（`getStatus`）返回：`level / isMember / points / exchangeCost / quotas { dialogue: {used, limit, remaining}, summary: {...} }`；管理员返回无限。
- 会员页与练习页可展示剩余额度，额度为 0 时引导兑换或开会员（付费墙触发时机见 [11 章](#11-会员转化设计)）。

### 3.6 额度防滥用与成本

- 所有 AI 调用先过 `checkAndDeduct`（管理员/会员/免费三级）。
- `recordTokens` 累计每日 token 用量，用于核算免费用户与付费用户的人均 AI 成本（DeepSeek 口径：输入约 1 元/百万 token、输出 2 元/百万 token）。
- `free_ai_corrections` / `free_ai_summaries` 可在后台动态调低（异常波动时先降配额再排查）。

## 4. 积分与邀请体系

### 4.1 积分规则（PointTransaction 全流水记录）

| 动作 | 积分 | type | 说明 |
|------|------|------|------|
| 每日签到 | +10 ~ +15 | `check_in` | 10 + min(streak-1, 5) |
| 邀请好友注册 | +100（邀请人） | `invite_reward` | 好友完成注册即到账 |
| 通过邀请码注册 | +50（被邀请人） | `invited_bonus` | 新人礼包 |
| 兑换 AI 次数 | -10 | `exchange` | 10 积分换 1 次 dialogue/summary |
| 订单积分抵扣 | -N | `redemption` | Web/支付宝/微信订单可用积分抵扣（`redeemPoints`） |

### 4.2 邀请码规则

- 邀请码：注册后自动生成（`GET /referral/code`），8 位大写字母数字。
- 邀请人：好友注册成功后 +5 天会员（`invite_trial_days` 可配）+100 积分，站内通知到账。
- 被邀请人：+50 积分，**不**额外赠送邀请会员天数。
- 已有会员叠加：`expiredAt = max(expiredAt, now) + days`。
- 防滥用：不能邀请自己、每个用户只能被邀请一次。

### 4.3 积分边界

- 积分只用于 App 内非现金权益与 Web 支付抵扣，**不直接影响 iOS IAP 价格**。
- iOS 优惠一律走 Apple introductory offer / offer codes / promotional offers。

### 4.4 新用户试用（Promo Trial）

- `POST /auth/promo-trial`：注册后调用，检查 `promo_trial_days`（默认 5 天）+ `promo_trial_max_claims`（默认 100 名额）限制，成功后 `promo_trial_claimed_count` +1。
- 免费赠送天数属于 App 自身业务权益，不走 Apple IAP；iOS 内不引导外部支付。

## 5. Apple / RevenueCat 配置

### 5.1 商品与权益 ID（三处必须一致）

```text
Entitlement ID:   pro_member
Product ID:       lourd.manyuding.app.monthly   # 月 19 元
                  lourd.manyuding.app.yearly    # 年 198 元
Offering:         default（Monthly + Annual 两个 package）
Bundle ID:        lourd.manyuding.app（Capacitor appId: lourd.manyu.app 需与 App Store Connect 一致）
```

- 旧 ID `lourd.manyu.pro.monthly/yearly` 已废弃，不补救，新 App 只接 `manyuding` 组。
- 前端 RevenueCat 包类型只保留 `monthly` / `yearly`，不保留 `lifetime`。

### 5.2 App Store Connect 关键配置

1. 订阅组：`ManYuDing Pro`（zh-Hans: 漫语町会员）；月卡、年卡放同一订阅组。
2. 月会员：`lourd.manyuding.app.monthly`，CNY 19，1 Month。
3. 年会员：`lourd.manyuding.app.yearly`，CNY 198，1 Year。
4. 首月优惠：**Pay As You Go，1 Month，CNY 14**，配置在月度订阅商品上（introductory offer）；前端文案"符合条件的新订阅用户首月 ¥14，之后 ¥19/月"，不承诺所有用户可用。
5. 审核信息：Review Screenshot、Display Name、Description、Price、Availability、本地化。

### 5.3 RevenueCat 配置

- 项目 → iOS App（Bundle ID `lourd.manyu.app`）→ 填 `VITE_REVENUECAT_API_KEY`（正式 key，禁测试 key/硬编码 fallback）。
- 连接 App Store Connect：
  - **In-App Purchase Key**（.p8 + Key ID + Issuer ID + Bundle ID）：StoreKit 2 交易验证。
  - **App Store Connect API Key**（.p8 + Key ID + Issuer ID + Vendor Number）：导入商品与价格。
  - **App-Specific Shared Secret（Legacy）**：iOS 15 / StoreKit 1 兼容兜底（部署目标 15.0），仍建议填写。
- 导入 Products → 创建 Entitlement `pro_member`（两个 product 都挂上）→ 创建 Offering `default`。
- Webhook 指向：`POST https://<域名>/api/v1/manyu/pay/revenuecat/webhook`（**后端已实现**，见 pay.controller）。
- `app_user_id` = 自有用户 ID，前端登录后 `revenueCat.identify(session.user.id)`。
- 建议监听事件：`INITIAL_PURCHASE / RENEWAL / UNCANCELLATION / CANCELLATION / EXPIRATION / BILLING_ISSUE / PRODUCT_CHANGE / REFUND`。
- webhook 更新 `user_membership` 规则：active entitlement → `status=active, expiredAt=expires_at`；expired/refunded → `expired/cancelled`；cancelled 未过期 → `autoRenew=false` 但会员有效到 `expires_at`。

### 5.4 前端行为（iOS Native）

- 展示 RevenueCat paywall；购买 / 恢复购买 / 管理订阅走 RevenueCat / Apple。
- iOS 不展示支付宝、微信购买按钮，不引导外部支付。
- 会员页必含：恢复购买、管理订阅、价格与周期、自动续订说明、取消方法、服务条款与隐私政策入口。

## 6. Web / Android 支付

- **Web**：支付宝 / 微信支付，积分可抵扣；后端 `POST /pay/orders` 创建订单 → 回调 `pay/callback/alipay`、`pay/callback/wechat` 更新 `user_membership`；非生产可用 `POST /pay/mock-confirm/:orderNo`。
- **Android**：上 Google Play 走 Google Play Billing + RevenueCat；国内安卓渠道按渠道规则拆（可能保留支付宝/微信）。
- 支付入口按平台隔离：iOS 只走 IAP，Web/Android 保留本地支付。

## 8. 生产监控与告警

```env

```

触发场景：后端 5xx、前端白屏/运行时错误、RevenueCat webhook 处理失败、订阅扣费异常、DB/文件资产容量接近阈值。

```text
GET /api/v1/manyu/health
```

`0` 表示不启用；COS/CDN 账单告警建议在云厂商控制台配置。

## 9. 内容发布与回滚

1. 管理员后台预览内容、学习包或移动 bundle。
2. 先发 staging 或低灰度 `rolloutPercent=5~20`。
3. 确认无错误后提升到 100；出错先 `enabled=false` 停用，不直接删除。
4. 保留上一版可用包，必要时重新启用旧版本。

| 功能 | 用途 |
|------|------|
| `enabled=false` | 快速停用移动 bundle / 内容包 |
| `rolloutPercent` | 灰度发布 |
| `channel=staging/production` | 测试/正式通道 |
| `minNativeVersion` | 防止旧 App 拉到不兼容的新 bundle |
| 保留旧版本 | 出错时回滚 |

## 10. 客服反馈闭环

- 字段：`status`（pending/resolved/closed）、`isCritical`、`adminNote`、`contact`。
- 最小处理规则：崩溃/支付/登录/数据丢失标记严重，当天处理；回复后状态改为已解决。

## 11. 会员转化设计

### 11.1 会员价值定位

不建议把主卖点表达为"AI 无限畅练、完整剧本、更多主题"，建议表达为：

> 每天 10 分钟，帮你从"不敢开口"练到"能完成真实对话"。

会员页最前面放三项：**每日个性化训练、AI 逐句纠错和改进建议、每周进步报告**；"不限次数/更多主题/完整剧情"作为补充权益。

### 11.2 免费版与会员版边界

免费版让用户**至少体验一次完整价值闭环**；会员版让价值持续发生。避免免费版太弱（未体验价值就付费）或太强（没有订阅理由）。

### 11.3 会员页改造方向

- 从"套餐说明页"变"个人进步页"：先展示"连续练习 4 天 / 完成 7 次真实对话 / 最常出现的问题"，再展示价格。
- 按钮文案按入口变化："解锁我的下一周训练 / 继续今天的 AI 复盘 / 查看完整进步报告"。

### 11.4 付费墙触发时机（按优先级）

1. 完成第一次 AI 对话并看到纠错结果后
2. 免费 AI 额度刚好用完时（与 3.5 节额度提示联动）
3. 连续学习 3 天后
4. 用户想继续下一章剧情 / 点击薄弱项专项训练时
5. 查看第一次周报时

场景化文案示例：

> 你今天已经完成 5 次 AI 纠错。开通会员，继续完成本次训练。

### 11.5 续费设计

- **每周进步报告**：展示开口分钟数、完成对话数、掌握新表达数、最常见问题、相比上周减少的问题、能力变化、下周重点。展示"变化"而非"活动量"（如"回答完整度 52% → 68%"）。
- **积累感会员资产**：专属学习计划、历史 AI 复盘、个人表达库、错误与薄弱项历史、剧情进度、能力曲线、周/月报告。会员到期**不删除**这些数据，明确告知"学习记录保留，个性化训练与完整复盘暂停"。

### 11.6 付费漏斗数据

推荐事件：`paywall_view / plan_selected / purchase_started / purchase_success / purchase_failed / purchase_restored / intro_offer_started / subscription_cancelled / subscription_expired / subscription_renewed / refund_detected`。

每次曝光携带：`paywall_source / user_learning_days / completed_sessions / current_streak / ai_quota_remaining / selected_plan / intro_offer_eligible / app_platform / app_version`。

`paywall_source` 至少区分：`ai_quota_exhausted / weekly_report / story_locked / profile / daily_task / weakness_training / expression_limit / onboarding`。

第一阶段重点指标：注册完成率、首次有效练习率、次日/7 日留存、完成 3 次以上练习比例、付费墙曝光率、各来源转化率、点击购买→支付成功转化率、购买前平均练习次数、月卡次月续费率、年卡选择比例、取消率与原因、退款率、免费/付费用户人均 AI 成本。

## 12. 小规模上线方案与决策表

### 12.1 四阶段方案

| 阶段 | 目标 | 关键动作 |
|------|------|----------|
| 一：20 位目标用户观察 | 验证首次体验 | 独立注册与首练、记录停顿/退出点、访谈价值理解 |
| 二：5~7 天价值体验 | 验证进步闭环 | 5~7 天完整会员体验、每天明确任务、第 7 天真实个人进步报告、基于个人数据的付费页 |
| 三：验证真实付费 | 验证付费意愿 | 不口头说服、记录未购买第一原因、对比两个付费墙版本、验证支付/恢复/取消/过期闭环 |
| 四：100 位付费用户 | 验证可持续 | 连续使用、可感知效果、次月续费、支付稳定、单人收入覆盖变动成本 |

### 12.2 上线决策表

| 决策 | 条件 |
|------|------|
| 进入小规模 TestFlight | 核心练习链路完整走通；月卡购买/到账/恢复通过真机测试；无严重数据丢失与崩溃；有人工客服与补偿能力；可收集行为与漏斗数据 |
| 公开上线但暂不投放 | P0 支付/审核项全完成；监控告警备份完成；App Review 材料齐全；≥20 目标用户完成真实体验；首次练习与 7 天链路无严重阻塞 |
| 开始扩大投放 | 已验证 ~100 位真实付费用户；能解释付费来源与未购买原因；次月续费有稳定趋势；退款率/故障率可接受；收入覆盖变动成本；内容供给与客服可承受增长 |
