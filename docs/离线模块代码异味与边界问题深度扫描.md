## 一、代码异味（Code Smells）

### 1.1 `;(()` 防御性分号前缀

**位置：** `daily-practice.repository.ts:329-342`

```ts
// 第329行
;((item.items ?? []) as any[]).forEach((prompt, idx) => push(prompt, idx))
// 第331行
;((item.vocabs ?? []) as any[]).forEach((prompt, idx) => push(prompt, idx))
// 第333-334行
;((item.patterns ?? []) as any[]).forEach((pattern, patternIndex) => {
  ;((pattern.items ?? []) as any[]).forEach((prompt, idx) => push(...))
})
// 第342行
;((item.items ?? []) as any[]).forEach((prompt, idx) => push(prompt, idx))
```

**问题：** `;` 前缀是防御 ASI（自动分号插入）的写法。只有在不确定上一行是否以分号结尾时才有必要。这种写法说明：

- 函数过长，作者自己无法确定上下文
- 代码可能从不同文件拼接而来
- `items ?? []` 已经有兜底，`as any[]` 又做了一次类型断言——三层防御说明对数据结构不信任

**建议：** 将 `push` 的逻辑抽为独立函数，或者先把 `items` 赋值给局部变量：

```ts
const prompts = item.items ?? []
for (const [idx, prompt] of prompts.entries()) {
  push(prompt, idx)
}
```

### 1.2 SHA-256 实现中的死代码（写后即弃）

**位置：** `asset-cache.service.ts:66-72`

```ts
// 第67-68行：创建临时 DataView，写长度，然后丢弃
new DataView(buf.buffer).setUint32(totalLen - 4, ml >>> 0, false)
new DataView(buf.buffer).setUint32(totalLen - 8, (ml / 0x100000000) >>> 0, false)

// 第71行：注释说"修正"，重新创建 DataView 做正确的事
// Correct 64-bit big-endian length:
const dv = new DataView(buf.buffer)
dv.setUint32(totalLen - 8, Math.floor(ml / 0x100000000), false)
dv.setUint32(totalLen - 4, ml >>> 0, false)
```

**问题：** 第 67-68 行的两个 `new DataView(...)` 创建了临时对象、写入了数据，但返回的 DataView 实例**立即被丢弃**（没有赋给变量）。紧接着第 71-74 行重新创建 `dv` 并做正确的事。这是典型的"先写了有 bug 的代码，后来修复但忘记删旧代码"。

而且第 67-68 行的位运算是错的（`ml / 0x100000000` 在 JS 中产生浮点数，`>>> 0` 对浮点数无意义），注释也承认了这一点。

**建议：** 删除第 67-68 行。

### 1.3 双重写入同一个 SQLite key

**位置：** `practice.repository.ts:286-310`

```ts
async completeSession(sessionId: string): Promise<PracticeSession | null> {
  const now = new Date().toISOString()
  // ★ 第一次写入：syncStatus = 'pending'
  await localDb.put('user_progress', {
    id: `practice-session:${sessionId}`,
    sessionId,
    status: 'completed',
    completedAt: now,
    updatedAt: now,
    syncStatus: 'pending',
  })
  const outboxItem = await syncOutbox.enqueue({
    entityType: 'practice_session',
    entityId: sessionId,
    operation: 'update',
    payload: { sessionId, status: 'completed', completedAt: now },
  })

  try {
    const result = await practiceApi.completeSession(await resolveSessionId(sessionId))
    await syncOutbox.markSynced(outboxItem.id)
    // ★ 第二次写入：同一个 id，syncStatus = 'synced'
    await localDb.put('user_progress', {
      id: `practice-session:${sessionId}`,
      sessionId,
      status: 'completed',
      completedAt: now,
      updatedAt: new Date().toISOString(),
      syncStatus: 'synced',
    })
    return result
  } catch {
    return null  // ★ 注意：这里返回 null，但第一次写入的 pending 记录还在
  }
}
```

**问题：**

1. 同一个 key `practice-session:${sessionId}` 在 10 行内被 `put` 两次。第一次写 `pending`，第二次写 `synced`。
2. 如果第二次 `put` 失败（如 SQLite 连接断开），数据库里永久留下 `pending` 记录，但实际上已经同步成功，下次 flush 可能重复处理。
3. `catch { return null }` 吞掉了所有异常，连日志都没有。调用方拿到 `null` 无法判断是"网络失败"还是"session 不存在"。

**建议：** 只在确定结果后写一次：

```ts
const syncStatus = result ? 'synced' : 'pending'
await localDb.put('user_progress', { id: `practice-session:${sessionId}`, ..., syncStatus })
```

### 1.4 `void` 满天飞——fire-and-forget 无错误边界

**位置：** 5 处

| 文件 | 行号 | 代码 |
|------|------|------|
| `daily-practice.repository.ts` | 530 | `void setLearningBadgeCount(0)` |
| `daily-practice.repository.ts` | 623 | `void setLearningBadgeCount(...)` |
| `daily-practice.repository.ts` | 666 | `void setLearningBadgeCount(...)` |
| `daily-practice.repository.ts` | 699 | `void setLearningBadgeCount(...)` |
| `learning.repository.ts` | 124 | `void cacheAggregated(unitDetail.id, aggregated)` |
| `practice.repository.ts` | 585 | `void import('@/lib/native/learning-reminder')...` |

**问题：** `void expr` 等价于 `expr.catch(() => {})`——告诉 TypeScript "我不关心这个 Promise 的结果"。但如果这些 async 函数内部抛异常：

- `setLearningBadgeCount` 可能操作原生 Badge API 失败
- `cacheAggregated` 写 SQLite 失败
- 动态 `import()` 失败

这些异常会变成 **unhandled promise rejection**。在 iOS WKWebView 中，未捕获的 Promise rejection 可能导致 WebView 白屏或崩溃。

**建议：** 统一替换为 `.catch((err) => console.debug('[scope] non-critical error:', err))`。

## 二、边界处理问题

### 2.1 `resolveSessionId` 两个版本语义不一致

**版本 A：** `offline-sync.service.ts:18-22`

```ts
async function resolveSessionId(sessionId: string): Promise<string | null> {
  if (!sessionId.startsWith('local_session_')) return sessionId
  const mapped = await localDb.get<{ value: string }>('kv', `session-map:${sessionId}`)
  return mapped?.value ?? null  // ← 返回 null 表示"本地session尚未映射到远程"
}
```

**版本 B：** `practice.repository.ts:53-56`

```ts
async function resolveSessionId(sessionId: string): Promise<string> {
  if (!sessionId.startsWith('local_session_')) return sessionId
  const mapped = await localDb.get<{ value: string }>('kv', `session-map:${sessionId}`)
  return mapped?.value ?? sessionId  // ← 返回原值作为 fallback
}
```

**问题：**

- 版本 A 返回 `null`（语义："还没同步，没有远程 ID"）
- 版本 B 返回原 `sessionId`（语义："没有远程 ID 就用本地的"）
- 版本 B 的调用方（`submitTurn`、`completeSession`、`analyzeSession`）会拿着 `local_session_xxx` 去调远程 API → **必然 404**

这是一个**潜在的运行时 bug**：当 session 尚未同步时，版本 B 返回的 `local_session_xxx` 被当作远程 ID 使用，API 返回 404，但被 `catch {}` 静默吞掉。

**建议：** 统一为版本 A（返回 `null`），调用方检查 `null` 并做相应处理。

### 2.2 Warmup 记录同步失败后 outbox 中的 payload 不完整

**位置：** `practice.repository.ts:456-466`

```ts
// submitWarmupRecords 中：
try {
  await warmupRecordApi.save(topicId, items)
  await warmupRecordApi.assess(topicId, topicTitle, items)
  // ... 标记 synced
} catch (err) {
```

**问题：** 如果 `save()` 成功但 `assess()` 失败，outbox 中的 payload 没有记录"save 已经成功"这一事实。下次 `replayItem` 处理时，会走 `syncApi.push()` 再调一次 `save`，可能导致后端重复记录。

```ts

  topicId, topicTitle, items, createdAt: now,

  assessCompleted: false, // ← 标记 assess 未完成
}
```

### 2.4 `catch {}` 空块——32 处静默吞异常

**完整统计：**

| 模式 | 数量 | 风险 |
|------|------|------|
| `catch { }` 完全空块 | 8 | 高：不知道什么失败了 |
| `catch { return null }` | 9 | 中：调用方不知道是"没数据"还是"出错了" |
| `catch { return [] }` | 5 | 中：同上 |
| `catch { /* 注释说明原因 */ }` | 3 | 低：至少有注释 |
| `catch { /* ignore */ }` | 4 | 中：注释和代码一样空洞 |
| 其他 | 3 | - |

**典型问题场景（`learning.repository.ts:271`）：**

```ts
async getUnitDetail(unitId: string): Promise<UnitDetail | null> {
  // ...
  try {
    const remote = await learningApi.getUnitDetail(unitId)
    await localDb.put('downloaded_unit_details', { ...remote, id: unitId })
    return remote
  } catch {
    // ★ 静默吞掉所有异常
    const cached = await localDb.get<any>('downloaded_unit_details', unitId)
    return cached ? aggregateUnitContent(cached) : null
  }
}
```

如果 `learningApi.getUnitDetail` 因为**登录过期**返回 401，这里会静默降级到旧缓存。用户看到的是旧数据，不知道需要重新登录。

**建议：** 至少区分"网络错误"（降级合理）和"认证错误"（应触发重新登录）。

## 三、数据流问题

### 3.1 Warmup 记录——三条路径写入，后端收到三套格式

这是本次审查发现的**最隐蔽的数据流问题**。

**路径 A：今日任务完成**

```
TodayTaskPage
  → dailyPracticeStore.submitToday()
    → dailyPracticeRepository.completeRun()
      → dailyPracticeApi.complete(payload)
        payload = { run: { date, scope, packIds, scheduledItemIds, completedItemIds, stats },
                    attempts: [...] }
      → 失败后入 outbox(entityType='daily_practice')
```

**路径 B：引导式热身完成**

```
GuidedWarmupPage
  → dailyPracticeRepository.syncAdHocRun(params)
    → practiceRepository.markTodayActivity(...)
    → practiceRepository.upsertLocalWarmupRecord(...)  // 写入 warmup_records 表
    → dailyPracticeApi.complete(payload)
      payload = { run: {...}, attempts: [...] }
    → 失败后入 outbox(entityType='daily_practice')
```

**路径 C：普通热身提交**

```
WarmupPage
  → practiceRepository.submitWarmupRecords(topicId, topicTitle, items)
    → localDb.put('warmup_records', ...)  // 直接写本地
    → warmupRecordApi.save(topicId, items)  // 调远程
    → warmupRecordApi.assess(topicId, topicTitle, items)
    → 失败后入 outbox(entityType='warmup_records')
      payload = { topicId, topicTitle, items, createdAt }
```

**问题汇总：**

| 维度 | 路径 A | 路径 B | 路径 C |
|------|--------|--------|--------|
| 远程 API | `dailyPracticeApi.complete` | `dailyPracticeApi.complete` | `warmupRecordApi.save` + `assess` |
| outbox entityType | `daily_practice` | `daily_practice` | `warmup_records` |
| payload 结构 | `{run, attempts}` | `{run, attempts}` | `{topicId, items}` |
| warmup_records 本地表 | 不写 | 写（通过 upsertLocalWarmupRecord） | 写（submitWarmupRecords 内直接写） |
| flush 时的 replay 逻辑 | `dailyPracticeApi.complete(payload)` | 同上 | `syncApi.push([{entityType:'warmup_records',...}])` |

**后果：**

1. 后端 `/sync/push` 接口收到两套不同格式的 warmup 数据，需要两套处理逻辑
2. 路径 C 的 warmup 记录**不走** `dailyPracticeApi.complete`，所以不会触发后端的排期更新（SM-2 状态机）
3. 如果用户在路径 C 提交后立即查看"我的学习"进度，进度计数不会更新（因为进度来自 `daily_practice_items` 表，而路径 C 不更新这个表）

### 3.2 同步方向不一致——push 和 pull 使用不同的数据通道

**Push（客户端→服务端）：**

```
outbox → offlineSyncService.flush()
  ├── my_unit, word/chunk/pattern_entry → syncApi.push() 批量
  ├── practice_session, practice_turn → replayItem() 逐条
  ├── warmup_records → replayItem() → syncApi.push() 单条
  ├── daily_practice → replayItem() → dailyPracticeApi.complete()
  └── learning_pack → replayItem() → 直接标记完成（不推服务端）
```

**Pull（服务端→客户端）：**

```
offlineSyncService.pull() → syncApi.pull(cursor) → applyUserPullChanges()
  ├── expressionItems → learningContentRepository.saveRemoteExpressionEntry()
  ├── sceneProgresses → localDb.put('user_progress', ...)
  ├── chunkProgresses → localDb.put('user_progress', ...)
  ├── practiceSessions → applyPracticeSessionItem() → localDb.put('practice_records', ...)
  ├── practiceWarmupRecords → applyWarmupRecordItem() → localDb.put('warmup_records', ...)
  └── deleted: expressionItems, sceneProgresses, chunkProgresses
```

**不对称之处：**

- Push 时 `learning_pack` 不推服务端（合理，这是本地概念）
- Pull 时**没有 `learning_pack`**（也合理）
- 但 Push 时 `daily_practice` 走 `dailyPracticeApi.complete()`，而 Pull 时没有对应的拉取逻辑——`daily_practice_items` 的远端进度只能通过 `dailyPracticeApi.progress()` 单独拉取（在 `buildTodayPlan` 中）
- `practiceTurns` 在 Pull 中被注释掉了（`// const practiceTurns = ...`），意味着服务端的 turn 数据不会同步回客户端

### 3.3 `dailyPracticeApi.progress()` 在 `buildTodayPlan` 中静默调用

**位置：** `daily-practice.repository.ts:548-558`

```ts
// 后台静默同步进度，不阻塞 UI
dailyPracticeApi.progress(itemIds)
  .then(async (remote) => {
    const pendingAttempts = await localDb.list<DailyPracticeAttempt>('daily_practice_attempts')
    const pendingItemIds = new Set(
      pendingAttempts.filter(a => a.syncStatus !== 'synced').map(a => a.itemId)
    )
    const safeItems = remote.items
      .filter(item => !pendingItemIds.has(item.itemId))
      .map(item => ({ ...item, id: item.itemId }))
    if (safeItems.length > 0) await localDb.putMany('daily_practice_items', safeItems)
  })
  .catch(() => { /* offline: local state is enough */ })
```

**问题：**

1. 这是一个**旁路同步**——不走 `offlineSyncService`，不走 outbox，不更新 cursor
2. "不覆盖本地未同步的进度"（`safeItems` 过滤）是正确的，但没有任何机制确保服务端进度最终会覆盖本地
3. 如果 `dailyPracticeApi.progress()` 成功但 `localDb.putMany` 失败，远端进度丢失
4. `catch(() => {})` 完全空——连日志都没有

### 3.4 "先出队再立即 HTTP" 的反模式

**位置：** `practice.repository.ts:265-278`

```ts
async submitTurn(sessionId, data) {
  // 1. 先入队 outbox
  const outboxItem = await syncOutbox.enqueue({
    entityType: 'practice_turn',
    entityId: turnRecordId(sessionId, data.round),
    operation: 'create',
    payload: { sessionId, data },
  })

  // 2. 立即尝试 HTTP
  try {
    const remoteSessionId = await resolveSessionId(sessionId)
    await practiceApi.submitTurn(remoteSessionId, data)
    await syncOutbox.markSynced(outboxItem.id)  // 成功→标记删除
  } catch (err) {
    // 失败→outbox 保留，等待下次 flush
  }
}
```

**问题：** 这种模式在 `createSession`、`submitTurn`、`completeSession`、`submitWarmupRecords` 中反复出现。它混合了两个关注点：

- **离线队列**（outbox）——保证数据不丢失
- **即时同步**（直接 HTTP）——优化在线体验

这两个关注点应该分离。当前混合方式的问题是：

1. 如果直接 HTTP 成功但 `markSynced` 失败（比如 SQLite 写入异常），outbox 中的记录还在，下次 flush 会**重复提交**
2. `syncOutbox.markSynced` 是**直接删除**记录（见前一个审查文档 §2.2.2），没有"已同步"的中间状态
3. 后端需要对同一个 turn 做幂等处理（当前后端确实用 `round` 做 upsert，但并非所有实体都有幂等保证）

**建议：** 统一为：只写 outbox → 触发异步 flush（不 await）→ flush 内部处理去重。

## 四、并发与竞态

### 4.1 `processDownloadQueue` 的 check-then-act 不是原子的

**位置：** `learning.store.ts:716-728`

```ts
async function processDownloadQueue() {
  const state = useLearningStore.getState()
  const running = state.downloadTasks.filter(
    (t) => t.status === 'downloading' || t.status === 'extracting',
  ).length
  if (running >= MAX_CONCURRENT_DOWNLOADS) return  // ← 检查

  const next = state.downloadTasks.find((t) => t.status === 'queued' && ...)
  if (!next) return

  useLearningStore.setState((s) => ({
    downloadTasks: s.downloadTasks.map((t) =>
      t.packId === next.packId ? { ...t, status: 'downloading', progress: 0 } : t,
    ),  // ← 设置为 downloading
  }))
  // ... 开始下载
}
```

**问题：** `getState()` → 检查 → `setState()` 之间没有锁。两个几乎同时的调用可能：

1. 调用 A 读取 `running = 1`，找到 `next = packX`，设置 `packX` 为 `downloading`
2. 调用 B 读取 `running = 1`（因为 A 的 `setState` 还没被 React batch 处理），也找到 `packX`（因为 `queued` 状态还没变），也设置 `packX` 为 `downloading`

结果：同一个 pack 被启动两次下载。

虽然 `activePackTaskIds` Set 提供了部分保护（在 `processDownloadQueue` 内部会 `add`），但 `setState` 的回调和 `activePackTaskIds.add` 之间仍有间隙。

**建议：** 使用一个模块级 `isProcessing` 标志：

```ts
let isProcessing = false
async function processDownloadQueue() {
  if (isProcessing) return
  isProcessing = true
  try { /* ... */ } finally { isProcessing = false }
}
```

### 4.2 Zustand `subscribe` 中同步写 localStorage

**位置：** `learning.store.ts:853-855`

```ts
useLearningStore.subscribe((state) => {
  persistPackTasks(state.downloadTasks)
})
```

**问题：** Zustand 的 `subscribe` 在**每次 state 变化**时同步触发。而下载过程中 state 变化非常频繁（progress 更新可能每秒 10+ 次）。每次变化都触发 `JSON.stringify` + `localStorage.setItem`。

如果一个下载任务有 50 次进度更新，就会产生 50 次 localStorage 写入。虽然浏览器有节流机制，但在 Capacitor WebView 中，`localStorage.setItem` 是同步 I/O（阻塞主线程）。

**建议：** 加 debounce（如 500ms）：

```ts
let persistTimer: ReturnType<typeof setTimeout> | null = null
useLearningStore.subscribe((state) => {
  if (persistTimer) clearTimeout(persistTimer)
  persistTimer = setTimeout(() => persistPackTasks(state.downloadTasks), 500)
})
```

### 4.3 `sqlite-json-store.ts` 的写队列实现有隐患

**位置：** `sqlite-json-store.ts:350-358`

```ts
async function enqueueWrite<T>(operation: () => Promise<T>): Promise<T> {
  const run = writeQueue.then(operation, operation)
  writeQueue = run.then(
    () => undefined,
    () => undefined,  // ← 错误被静默吞掉
  )
  return run
}
```

**问题：** `.then(operation, operation)` 意味着**即使前一个操作失败，下一个操作也会继续执行**。这是有意为之（防止一个失败的写入阻塞整个队列）。但：

1. 失败的异常被 `.then(() => undefined, () => undefined)` 完全吞掉
2. 调用方拿到的 `run` Promise 会正常 reject（因为 `run = writeQueue.then(operation, operation)`），但队列状态被重置了
3. 如果 operation A 失败后 operation B 成功，A 的调用方看到错误，B 的调用方看到成功——但 A 的数据确实没写入，这可能导致数据不一致

**当前影响：** 低。因为 SQLite 写入失败极少发生（通常是磁盘满或数据库损坏）。但如果发生，会导致静默数据丢失。

## 五、其他问题

### 5.1 `learning-pack.service.ts` 中 `asset_refs` 预加载 Map 的 key 不是唯一键

**位置：** `learning-pack.service.ts:568-573`

```ts
const allRefsList = await localDb.list<any>('asset_refs')
const refsBySha256 = new Map<string, any>()
for (const ref of allRefsList) {
  if (ref.sha256) refsBySha256.set(ref.sha256, ref)
}
```

**问题：** 同一个 SHA256 可能被多个包引用，`asset_refs` 中会有多条记录（每条对应一个 `packId:sha256` 的 id）。但这里的 Map 以 `sha256` 为 key，**后面的记录会覆盖前面的**。

虽然在这个场景中，只关心"是否存在"（不关心具体是哪个包的引用），所以覆盖不影响正确性。但如果未来需要读 `ref.ext` 等字段，可能读到错误的值。

### 5.2 `arrayBufferToBase64` 对大文件的栈溢出风险

**位置：** `asset-cache.service.ts:168-174`

```ts
function arrayBufferToBase64(buffer: ArrayBuffer) {
  const bytes = new Uint8Array(buffer)
  let binary = ''
  const chunkSize = 0x8000
  for (let i = 0; i < bytes.length; i += chunkSize) {
    binary += String.fromCharCode(...bytes.subarray(i, i + chunkSize))
  }
  return btoa(binary)
}
```

**问题：** `String.fromCharCode(...bytes)` 使用 spread 运算符。虽然分块大小是 32KB（`0x8000`），理论上不会超栈。但 `binary` 字符串会不断增长——对于一个 10MB 的资源文件，`binary` 字符串会在内存中达到约 13MB，然后传给 `btoa` 再产生一个约 13MB 的字符串。

对于移动端（内存有限），10MB 的音频/图片资源可能导致内存压力。

**建议：** 考虑流式 Base64 编码或直接使用 Capacitor Filesystem 的 `blob` 写入（避免 Base64 编码）。
