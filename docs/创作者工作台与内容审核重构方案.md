# 创作者工作台、内容隔离与发布审核重构方案（讨论稿）

> 状态：讨论稿，暂不进入开发  
> 目标：在不破坏现有学习包、小说包、写作包、练习包、阅读包、听力包和剧情包数据结构的前提下，增加“创作者”角色、按创作者隔离内容，并建立管理员审核后才能生成发布包的流程。

## 1. 结论摘要

整体方向合理，而且很有必要。创作者不应该获得完整后台权限，也不应该直接生成用户实际下载和使用的最新版内容包。

建议将现有“后台管理”拆成同一套后台框架下的两个视角：

- 管理员进入“后台管理”，可以查看和操作所有数据。
- 创作者进入“创作管理”，只能查看和操作自己的内容，以及被允许使用的共享基础数据。
- 普通用户在网页端不显示任何后台入口。
- 创作者提交发布审核后，由管理员在“反馈管理”的“内容审核”页签处理；审核通过后由服务端基于已审核快照生成版本，创作者不能直接调用生成接口。

这里最重要的不是隐藏菜单，而是同时落实三层限制：前端路由、后端权限、数据库查询范围。只做菜单隐藏会留下越权访问和跨用户修改风险。

## 2. 对现有实现的核查

### 2.1 网页首页与账号页

- 当前桌面端页头头像会跳转 `/account`。
- `/account` 同时承载账号信息、账号绑定和密码修改，并不是首页自动跳转目标；登录后的通用跳转目前是 `/`。
- 当前只有 `admin` 会看到“后台管理”按钮，普通用户本来就不会看到。
- 移动端的个人资料、账号绑定和退出功能另有入口，因此“网页端取消 `/account` 页面”可以只影响 Web，不需要删除移动端账号能力。

建议的 Web 行为：

- 页头头像改为简洁下拉菜单，不再跳 `/account`。
- 菜单只保留用户名称/邮箱、角色对应的管理入口、退出登录。
- `admin` 显示“后台管理”；`creator` 显示“创作管理”；`user` 不显示管理入口。
- Web 访问旧地址 `/#/account` 时重定向到 `/#/`，兼容旧收藏和历史链接。
- Capacitor 端继续保留现有账号设置、绑定和退出功能。

### 2.2 当前角色与权限

当前 `UserRole` 只有：

- `user`
- `admin`

大部分内容管理接口直接判断 `role === 'admin'`。因此新增 `creator` 后，不能简单把这些判断全部改成“管理员或创作者”；每类接口还需要独立的能力权限和数据范围判断。

### 2.3 当前内容归属

现有 `Scene`、`TrainingTopic`、`LearningPackage`、`InkScript`、`GameCharacter`、`TtsVoiceAsset` 等核心内容表没有统一的创作者归属字段。部分写操作会记录文件引用的操作用户，但这不能作为内容所有权。

因此目前无法可靠实现：

- 创作者只看自己的学习包和剧情包；
- 创作者只能修改自己的话题、故事、角色和音色；
- 管理员列表展示创作者；
- 防止创作者通过猜测 ID 访问或修改他人的内容。

### 2.4 当前发布与分页

- 学习包发布管理当前允许管理员直接“生成最新版/首版”，生成接口可以直接产出 `published` 版本。
- 剧情包发布复用了学习包发布页面的 `script` 模式，仍缺少创作者审核闸门。
- `/admin/nqtr` 中的故事列表已有后端分页和简单上一页/下一页控件，当前每页 50 条；但页面预加载的角色、地点及部分话题数据仍存在全量读取。
- `/admin/narrative-assets` 的角色、音色、地图均为全量读取，没有分页。

所以“增加分页”应定义为：所有列表数据源都采用服务端分页，而不只是页面最外层出现翻页按钮。

## 3. 角色与能力模型

数据库角色扩展为：

```text
user | creator | admin
```

建议后端不要散落字符串判断，而是建立统一授权能力：

```text
content.read.own
content.write.own
content.read.all
content.write.all
release.submit
release.review
release.generate
asset.read.own
asset.write.own
asset.read.all
user.manage
system.manage
```

第一阶段仍可由角色静态映射能力，不必立即建设复杂 RBAC 表。这样既能控制改造范围，也避免以后继续复制 `role === 'admin'`。

### 3.1 权限矩阵

| 能力 | 普通用户 | 创作者 | 管理员 |
|---|---:|---:|---:|
| 使用前台学习功能 | 是 | 是 | 是 |
| 进入管理区域 | 否 | 是，显示“创作管理” | 是，显示“后台管理” |
| 查看/编辑自己的内容 | 否 | 是 | 是 |
| 查看/编辑其他人的内容 | 否 | 否 | 是 |
| 提交版本审核 | 否 | 是 | 是 |
| 审核内容 | 否 | 否 | 是 |
| 生成正式最新版 | 否 | 否 | 是/管理员审核动作触发 |
| 用户、会员、账单、反馈、通知、系统设置 | 否 | 否 | 是 |

## 4. 创作者菜单与路由范围

创作者只显示两个菜单组。

### 4.1 内容管理

- 学习包管理（现“学习包内容”）
- 练习话题
- 学习包发布管理

### 4.2 剧情管理

- 剧情包内容
- 剧情共享资产
  - 角色资产
  - 音色资产
  - 不显示地图世界
- 剧情包发布管理（建议把当前“剧本包发布管理”统一改名为“剧情包发布管理”）

管理员保持现有完整菜单，并新增内容审核入口；为满足“审核发送到反馈管理”，入口放在：

```text
用户与运营
└─ 反馈管理
   ├─ 用户反馈
   └─ 内容审核
```

路由必须同菜单一样受保护。创作者直接输入未授权 URL（如 `/admin/users`、`/admin/maps`）时返回 403 页面或跳转到其默认创作页，不能仅靠侧栏隐藏。

建议默认入口：

- 管理员：`/admin/users` 或现有默认页。
- 创作者：`/admin/learning-content`。

## 5. 内容所有权设计

### 5.1 归属原则

建议采用“根实体显式归属，子实体继承归属”的方式，减少重复字段不一致。

| 内容域 | 根实体归属字段 | 子数据的归属判断 |
|---|---|---|
| 学习包/小说/写作/练习/阅读/听力 | `Scene.ownerId` | `TrainingTopic`、教学材料、章节、`LearningPackage` 通过 `sceneId` 继承 |
| 学习包合集/分组 | `PackageGroup.ownerId` | `PackageGroupItem` 通过 `groupId` 继承；加入分组时校验 Scene 与分组同属一人 |
| 剧情故事 | `InkScript.ownerId` | 故事资产引用通过 `inkScriptId` 继承 |
| 剧情包章节 | 优先通过所属 `Scene.ownerId` | 独立未绑定故事使用 `InkScript.ownerId` |
| 角色资产 | `GameCharacter.ownerId` | 角色音色绑定通过 `characterId` 继承 |
| 音色资产 | `TtsVoiceAsset.ownerId` + `visibility` | 角色只能绑定自己可见的音色 |

字段建议：

```prisma
ownerId    String
owner      User     @relation(...)
createdAt  DateTime @default(now())
updatedAt  DateTime @updatedAt
```

管理员创建的数据也应有明确 `ownerId`，不要用 `null` 同时表达“系统数据”和“历史数据”。如确有全平台共享音色，额外增加：

```text
visibility = private | system_shared
```

创作者可见范围为：`ownerId = 当前用户`，以及产品明确允许引用的 `system_shared` 只读资产。按照本次需求，创作者自己创建的角色和自定义音色只有本人及管理员可见。

`SceneCategory` 更适合作为管理员维护的系统分类字典，创作者只读选择，不建议每位创作者各建一套同名分类。词汇、语块、句型等公共教学语料也应先保持系统只读；创作者在自己的包和话题中只保存引用或包内自定义内容。这样不会因为新增创作者而破坏现有教学数据结构。

### 5.2 为什么不能只在 LearningPackage 上加 ownerId

生成包只是源内容的版本产物。如果仅给 `LearningPackage` 加归属，创作者仍可能看到或修改别人的 `Scene`、`TrainingTopic`、`InkScript`，再生成自己的包，数据隔离仍然失效。因此所有权必须从源内容根实体开始。

### 5.3 后端数据范围

每个列表、详情、创建、更新、删除接口统一应用 `ContentScope`：

```text
admin   -> 不附加 owner 条件
creator -> where.ownerId = session.user.id
user    -> 禁止进入管理接口
```

对子实体必须通过父关系校验，例如创作者读取话题：

```text
where: {
  id: topicId,
  scene: { ownerId: currentUserId }
}
```

更新和删除同样必须带所有权条件，不能先按 ID 查出后直接更新。返回 404 比返回“这是别人的数据”更安全，避免泄露资源存在性。

管理员列表应返回创作者摘要：

```text
owner: { id, name, email }
```

并支持按创作者筛选和搜索。

### 5.4 历史数据迁移

建议分两阶段迁移，避免一次迁移导致线上不可用：

1. 增加可空 `ownerId`，将全部历史内容回填给指定管理员账号。
2. 校验无空值后改为必填，并增加索引。

需要为常用查询增加组合索引，例如：

```text
Scene(ownerId, updatedAt)
InkScript(ownerId, updatedAt)
GameCharacter(ownerId, createdAt)
TtsVoiceAsset(ownerId, updatedAt)
LearningPackage(sceneId, status, version)  // 现有索引保留
```

## 6. 发布审核流程

### 6.1 推荐状态机

不要把“源内容是否通过审核”和“ZIP 是否正在构建”混在现有 `LearningPackageStatus` 中。建议新建审核记录：

```text
draft/edited
    ↓ 创作者提交
pending
    ├─ rejected  → 创作者修改后重新提交
    ├─ canceled  → 创作者主动撤回
    └─ approved  → 服务端触发构建
                      ↓
                 building
                 ├─ build_failed
                 └─ published
```

`LearningPackageStatus` 继续描述构建产物状态；`ContentReviewRequest.status` 描述审核状态。两个概念分开后，失败重试和审核历史都更清楚。

### 6.2 审核记录

建议新建专用表，而不是直接把审核塞进现有 `Feedback` 表：

```text
ContentReviewRequest
- id
- kind: learning_package | narrative_package
- targetId: Scene.id
- ownerId
- requestedVersion
- sourceRevision / sourceHash
- snapshot（或指向不可变快照）
- status: pending | approved | rejected | canceled | superseded
- submittedAt
- reviewedById
- reviewedAt
- reviewNote
- generatedPackageId
- createdAt / updatedAt
```

原因：当前 `Feedback` 只有 `pending/resolved/closed`，没有目标版本、审核人、审核快照和防重复生成能力。硬塞进去会让用户反馈和内容发布逻辑耦合。

产品界面仍然可以完全满足“消息进入反馈管理”：管理员反馈管理页新增“内容审核”页签，以统一收件箱方式读取 `ContentReviewRequest`。也可以在反馈列表顶部显示待审核数量。

### 6.3 防止“审核后偷改内容”

这是发布审核最容易遗漏的风险。提交时必须记录不可变快照或内容哈希：

- 创作者提交后继续编辑，原申请自动标记为 `superseded`，需要重新提交。
- 管理员审核的是提交时的版本，不是随时变化的最新数据库内容。
- 审核通过时，由后端直接基于已审核快照排队生成；不再把“生成最新版”权限交还给创作者。
- 生成接口再次校验 `reviewRequest.status === approved`、目标、版本、哈希和申请人一致。

这比“管理员点通过，然后创作者再点生成”更安全，也减少一步操作。界面上创作者看到的按钮应为：

- 无申请：`提交审核`
- 审核中：`审核中`
- 被驳回：`修改后重新提交`
- 已通过/构建中：`生成中`
- 已发布：`已发布 vN`

管理员可以保留“直接生成”能力，但应记录操作日志；正常审核动作建议就是“审核通过并生成”。

### 6.4 并发与幂等

- 同一目标同一 `sourceRevision` 只能有一个有效审核申请。
- 同一目标同一版本只能生成一次，继续依赖现有 `(sceneId, version)` 唯一约束。
- 审核通过、创建任务和锁定版本号应放在同一事务内。
- 队列任务使用 `reviewRequestId` 作为幂等键，防止管理员重复点击生成多个任务。
- 构建失败不自动撤销审批；管理员可以基于同一已审批快照重试，重试需要留日志。

### 6.5 审核结果通知

- 提交时：在反馈管理的“内容审核”中出现一条待办。
- 通过/驳回时：给创作者发送站内通知。
- 驳回必须填写原因；通过说明可选。
- 通知跳回对应的发布管理页，并定位到目标内容。

## 7. 分页设计

统一使用服务端分页响应：

```json
{
  "items": [],
  "total": 0,
  "page": 1,
  "pageSize": 20,
  "totalPages": 0
}
```

统一规则：

- 默认 `pageSize = 20`，最大 `100`。
- 切换搜索词、筛选项、创作者或页签时重置到第 1 页。
- 搜索和筛选必须在数据库分页之前执行。
- 请求带角色数据范围，创作者的 `total` 只能统计自己的数据。
- 页码超过总页数时回到最后一页或返回空页，由前端纠正页码。

### 7.1 `/admin/nqtr`

当前故事列表已有分页，但需要统一改造：

- 将每页 50 条调整为统一的 20 条或允许切换 20/50。
- 使用已有 `AdminPagination`，替代组件内的简单“上一页/下一页”，保持后台一致。
- 练习话题列表必须传 `page/pageSize`，不再走兼容性的全量返回。
- 页面初始化所需角色/地点选择器改成可搜索分页选择，或仅在打开编辑器时按需加载。
- 创作者不显示地图，因此创作者的练习故事编辑器不能依赖全量地点数据；地点相关字段应隐藏或只读使用已有引用。

### 7.2 `/admin/narrative-assets`

- 角色资产：服务端分页、关键词搜索、按创作者筛选（仅管理员可见筛选）。
- 音色资产：服务端分页、关键词、供应商、可用状态筛选；创作者只看自己的自定义音色和允许引用的系统共享音色。
- 地图世界：只对管理员显示，并增加服务端分页。
- 三个页签维护独立页码，切换页签不互相污染。
- 统计数字使用接口返回的 `total`，不能再用“当前已加载数组长度”。

## 8. 前后端落地结构建议

### 8.1 后端

建议从当前大型 `ContentAdminController` 中逐步拆出按领域组织的控制器：

```text
content-management/
├─ content-authorization.service.ts
├─ learning-content.controller.ts
├─ narrative-content.controller.ts
├─ narrative-assets.controller.ts
├─ release-review.controller.ts
└─ release-review.service.ts
```

统一使用 Guard/Decorator 或授权服务，不继续在每个方法内复制角色字符串判断。控制器负责 DTO 和授权入口，查询、审核状态机和事务放在服务层。

所有分页和审核输入使用 DTO 校验，不再直接接收未约束的 `any` 或字符串页码。

### 8.2 前端

建议集中定义：

```text
role -> management label
role -> allowed route keys
role -> visible menu groups
```

菜单和路由守卫共用同一份配置，避免菜单已隐藏但路由仍可访问。按钮是否显示只能改善体验，真正权限仍以后端为准。

## 9. 建议实施顺序

1. 数据库增加 `creator`、内容 `ownerId`、索引并迁移历史数据。
2. 建立统一角色能力和后端数据范围，先补齐接口安全测试。
3. 将现有管理员行为保持不变，管理员列表增加创作者列和筛选。
4. 增加创作者菜单、路由守卫和 Web 页头简化。
5. 建立 `ContentReviewRequest`、审核快照、反馈管理“内容审核”页签和站内通知。
6. 收紧生成接口：创作者只能提交审核，管理员审批触发生成。
7. 完成 NQTR 与剧情共享资产的全链路分页。
8. 做历史数据、并发提交、跨用户越权和构建失败回滚测试。

## 10. 验收标准

### Web 首页

- 桌面网页点击头像不再进入 `/#/account`。
- Web 直接访问旧 `/account` 会回首页。
- 普通用户没有管理入口；创作者显示“创作管理”；管理员显示“后台管理”。
- 所有角色都能从简洁菜单退出登录。

### 权限与隔离

- 创作者只能看到指定的 6 个功能入口。
- 创作者看不到地图世界、用户运营和系统设置。
- 创作者无法通过 URL 或直接 API 访问未授权功能。
- 创作者列表、详情、更新、删除都只能操作自己的内容。
- 管理员能查看全部内容并看到创作者名称/账号。

### 审核发布

- 创作者页面不存在可直接调用的正式生成按钮。
- 提交后管理员在反馈管理的“内容审核”中看到申请。
- 审核内容在提交后被修改时，旧审批不能生成新内容。
- 管理员通过后仅生成审核过的版本，结果通知创作者。
- 重复点击、重复请求不会产生重复版本或重复任务。

### 分页

- NQTR 的故事、话题及大数据选择器不再一次性加载全量数据。
- 剧情共享资产三个管理员页签均使用服务端分页；创作者只出现角色和音色页签。
- 总数、筛选、搜索、翻页在管理员全量视角和创作者个人视角下均正确。

## 11. 需要产品确认的问题

1. 创作者能否使用管理员创建的“系统共享音色”？建议允许只读使用，否则每位老师都必须重复创建音色；创作者自建音色仍保持私有。
2. 创作者能否引用管理员创建的角色？按你当前描述，我倾向于不能，只能使用自己的角色；如果要允许，应给角色也增加 `system_shared` 可见性。
3. 审核通过后是否直接自动生成？建议“通过即排队生成”，最安全也最省操作。
4. 创作者编辑已发布内容时，线上旧版本是否继续可用？建议继续可用，直到新版本审核并生成成功后再切换。
5. 创作者是否允许删除已有发布版本的源内容？建议不允许硬删除，只能归档；管理员可执行受审计的强制删除。

## 12. 方案评价

这个产品设计的核心思路是对的：创作者专注生产，管理员把控进入正式内容体系的版本。建议坚持“共享编辑后台、权限视角不同”，不要复制一套独立创作者后台；否则学习包和剧情包结构会产生两套实现并逐渐分叉。

我认为需要重点坚持的三条底线是：

- 内容所有权必须落库并在后端强制过滤。
- 审核必须绑定不可变版本/快照，不能只审核一个会继续变化的内容 ID。
- 审核记录使用独立领域模型，但在反馈管理里统一展示，既满足运营入口统一，也避免污染用户反馈数据。
