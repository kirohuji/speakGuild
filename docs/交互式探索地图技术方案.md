# SpeakGuild 交互式探索地图技术方案

> 目标：在现有 `GameMap → GameLocation → GameRoom` 内容模型和 PixiJS 编辑器基础上，实现类似 Summer Town 的分层插画地图、拖拽缩放、建筑悬停、镜头聚焦和内容入口。

产品业务、英语学习循环、剧情包绑定、房间物品和素材生产方案见
[英语剧情探索地图产品与素材调研.md](./英语剧情探索地图产品与素材调研.md)。

## 1. 结论

本项目建议继续使用 **PixiJS + React 的混合方案**：

- PixiJS 负责地图底图、建筑精灵、装饰层、命中区域、拖拽缩放和镜头动画。
- React 负责工具栏、属性面板、筛选器、建筑详情卡、确认弹窗和路由。
- 数据层继续保留 `GameMap → GameLocation → GameRoom`，不要为了视觉地图推翻现有导航模型。
- 在 `GameMap.editorData` 中逐步引入有版本的地图文档，补足图层、锚点、层级、旋转、交互行为等视觉信息。

Summer Town 的 DOM 分层方案适合静态展示型小地图，但 SpeakGuild 已经具备 PixiJS 编辑器，并计划支持地图编辑、动态对象、NPC、触发器和运行时探索。切回纯 DOM 会形成两套渲染逻辑，收益不大。

## 2. 参考地图的实现原理

Summer Town 并没有使用地理地图或 3D 引擎。它的核心结构是：

1. 一张完整的插画底图。
2. 每座可交互建筑是一张独立透明 PNG。
3. 所有元素放在固定尺寸的世界坐标系中。
4. 拖拽和缩放通过移动、缩放整个世界容器实现。
5. 建筑使用独立热区处理 hover 和 click。
6. 点击建筑后，相机动画聚焦到建筑锚点，同时由 React 打开详情卡。

这些设计和 PixiJS 并不冲突。DOM 中的 `<img>` 可以直接对应 PixiJS 的 `Sprite`，绝对定位容器对应 PixiJS 的 world `Container`，CSS `translate + scale` 对应 world container 的 `position + scale`。

## 3. 当前项目现状

### 3.1 已有数据层

后端已有三个稳定的业务实体：

```text
GameMap
└── GameLocation
    └── GameRoom
        └── GameRoomNpc
```

当前字段已经覆盖第一版探索地图的大部分需要：

| 能力 | 当前字段 |
| --- | --- |
| 地图底图 | `GameMap.backgroundUrl` |
| 世界尺寸 | `GameMap.width`, `GameMap.height` |
| 扩展编辑数据 | `GameMap.editorData` |
| 建筑/地点图片 | `GameLocation.icon` |
| 地点位置 | `GameLocation.posX`, `GameLocation.posY` |
| 建筑显示尺寸 | `GameLocation.iconWidth`, `GameLocation.iconHeight` |
| 进入地点后的背景 | `GameLocation.backgroundUrl` |
| 声音资源 | `GameLocation.bgmUrl`, `GameLocation.ambientUrl` |
| 解锁和可见性 | `required*`, `disabled`, `hidden`, `isPreview` |
| 房间入口 | `GameRoom.icon`, `backgroundUrl`, `isEntrance` |
| 内容关联 | `sceneId`, `inkScriptId`, `GameRoomNpc` |

因此现有数据可以和 Summer Town 的设计组合，不需要重做业务表。

### 3.2 已有渲染器

`ExplorationPixiCanvas` 已经实现：

- PixiJS 8 和 `@pixi/react` 初始化。
- 地图背景纹理加载。
- 地点图片精灵。
- hover/选中描边和轻微脉冲。
- 拖动地点并保存坐标。
- 单击选择、双击进入。
- React 编辑器外壳和 Pixi 舞台分工。

这已经是正确的技术方向。

### 3.3 当前限制

当前实现还不能直接成为正式运行时地图，主要有以下问题：

1. 世界尺寸写死为 `1600 × 900`，没有读取 `GameMap.width/height`。
2. `posX/posY` 按 `0–100` 百分比解释，精细编辑、对象排序和地图扩展会受到限制。
3. 画布只做“适应窗口”，尚无玩家视角的平移、滚轮缩放、触控缩放和边界回弹。
4. `ExplorationNode` 只表示地点热区，无法表达装饰、触发器、粒子、前景遮挡等对象。
5. 精灵锚点固定为中心，不适合建筑图片常用的“底部中心落地”。
6. 缺少 `zIndex` 或按 Y 坐标排序，前后遮挡关系不能稳定表达。
7. 编辑器直接在 `pointerup` 调接口，连续编辑时会产生较多请求。
8. `editorData` 使用 `any`，已有房间布局结构但没有统一版本类型和校验。

## 4. 为什么选择 PixiJS

### 4.1 方案比较

| 维度 | DOM 分层图片 | PixiJS |
| --- | --- | --- |
| 少量静态建筑 | 简单 | 简单 |
| 大量装饰/NPC/粒子 | DOM 数量容易膨胀 | 更适合 |
| 高频拖拽和镜头动画 | 可实现 | 更自然 |
| 编辑器变换控件 | 需要自行组织 DOM | 已有舞台基础 |
| 图层和 Y 排序 | CSS z-index | Container/sortableChildren |
| 点击详情卡和表单 | 很适合 | 应交给 React |
| 与现有项目集成 | 需要新增渲染器 | 已经集成 |
| 后续碰撞/路径/特效 | 扩展成本高 | 扩展空间更大 |
| 无障碍语义 | 更好 | 需要额外 DOM 辅助层 |

### 4.2 最终边界

不要把整个页面都画进 Canvas。

```text
React 页面
├── Navbar / HUD
├── 筛选和任务提示
├── PixiMapViewport
│   ├── backgroundLayer
│   ├── decorationLayer
│   ├── locationLayer
│   ├── npcLayer
│   ├── foregroundLayer
│   └── effectLayer
├── LandmarkDetailDialog
└── AccessibilityOverlay
```

Pixi 只负责“世界内”的内容；详情、表单、文本密集界面和导航继续使用 React DOM。

## 5. 数据组合方式

### 5.1 业务实体与视觉对象分离

`GameLocation` 表示“玩家能进入的地点”，不应同时承担树木、路灯、云、波纹、不可见触发区等所有视觉对象。

推荐关系：

```text
GameLocation（业务导航）
        ↑ locationId
MapObject（视觉表现）
```

一个地点通常对应一个 `type: "location"` 的 MapObject；装饰物不需要创建虚假的 GameLocation。

### 5.2 推荐的 editorData v3

第一阶段可以继续存储在 `GameMap.editorData`，避免立即新增数据库表：

```ts
interface ExplorationMapDocumentV3 {
  version: 3;
  coordinateMode: "world";
  canvas: {
    width: number;
    height: number;
    backgroundUrl?: string;
    minZoom: number;
    maxZoom: number;
    initialView?: CameraTarget;
  };
  layers: MapLayer[];
  objects: MapObject[];
  roomLayouts?: Record<string, Record<string, RoomLayout>>;
}

interface CameraTarget {
  x: number;
  y: number;
  zoom: number;
}

interface MapLayer {
  id: string;
  name: string;
  kind:
    | "background"
    | "decoration"
    | "location"
    | "npc"
    | "foreground"
    | "effect";
  order: number;
  visible: boolean;
  locked: boolean;
}

interface MapObject {
  id: string;
  type: "location" | "sprite" | "trigger" | "decoration" | "effect";
  layerId: string;
  assetUrl?: string;
  locationId?: string;
  roomId?: string;
  transform: {
    x: number;
    y: number;
    width?: number;
    height?: number;
    scaleX?: number;
    scaleY?: number;
    rotation?: number;
    anchorX?: number;
    anchorY?: number;
    zIndex?: number;
  };
  hitArea?: {
    shape: "rect" | "circle" | "polygon";
    points?: number[];
    width?: number;
    height?: number;
    radius?: number;
  };
  camera?: {
    focusX?: number;
    focusY?: number;
    zoom?: number;
  };
  interaction?: {
    enabled: boolean;
    hoverEffect?: "lift" | "glow" | "pulse" | "none";
    action?: "open_location" | "open_room" | "open_dialog" | "emit_event";
    payload?: Record<string, unknown>;
  };
  visibleWhen?: {
    requiredOutputLevel?: string;
    requiredFlags?: Record<string, unknown>;
  };
}
```

### 5.3 与现有字段的映射

| 现有数据 | 新视觉文档 |
| --- | --- |
| `GameMap.width/height` | `canvas.width/height`，两者应保持一致 |
| `GameMap.backgroundUrl` | 默认底图；文档可引用但不重复作为权威来源 |
| `GameLocation.posX/posY` | 迁移为 MapObject 世界坐标 |
| `GameLocation.icon` | `MapObject.assetUrl` 的默认值 |
| `iconWidth/iconHeight` | `transform.width/height` |
| `GameLocation.id` | `MapObject.locationId` |
| `GameLocation.hidden/disabled` | 运行时业务可见性和可交互性 |
| `explorationScenes` | 迁移到 `roomLayouts`，保留兼容读取 |

建议规定权威来源：

- 名称、描述、解锁条件、内容入口由 `GameLocation` 管理。
- 坐标、锚点、图层、旋转、命中区域、镜头参数由 `MapObject` 管理。
- 图片第一阶段可继续从 `GameLocation.icon` 读取；后续允许 MapObject 覆盖，便于同一地点在不同地图使用不同外观。

## 6. 坐标迁移

当前地点坐标是百分比：

```ts
screenX = (posX / 100) * worldWidth;
screenY = (posY / 100) * worldHeight;
```

迁移到世界坐标：

```ts
worldX = (posX / 100) * map.width;
worldY = (posY / 100) * map.height;
```

兼容策略：

1. `editorData.version < 3` 时，将 `GameLocation.posX/posY` 视为百分比。
2. 加载时生成内存中的 v3 MapObject。
3. 用户第一次保存新版地图时写入 `editorData.version = 3`。
4. 迁移期继续回写 `posX/posY` 百分比，保证旧管理页仍能工作。
5. 所有消费者切换完成后，再停止双写。

不要直接改变 `posX/posY` 的单位，否则旧数据会被误解。

## 7. 运行时相机

### 7.1 相机模型

```ts
interface MapCamera {
  x: number;
  y: number;
  zoom: number;
}
```

将相机应用到 world container：

```ts
world.position.set(camera.x, camera.y);
world.scale.set(camera.zoom);
```

### 7.2 输入能力

正式运行时应支持：

- 鼠标左键和单指拖拽平移。
- 滚轮围绕指针位置缩放。
- 双指 pinch 缩放。
- `+/-` 按钮缩放。
- “复位”按钮返回初始镜头。
- 拖出边界时阻尼，松手后回弹。
- `prefers-reduced-motion` 下缩短或关闭大幅镜头动画。

### 7.3 点击地点后的镜头

MapObject 可以配置：

```ts
camera: {
  focusX: 1380,
  focusY: 720,
  zoom: 2.4
}
```

没有配置时使用对象锚点和尺寸自动计算。聚焦完成后，由 React 打开详情卡；关闭详情卡时恢复先前镜头。

镜头动画可使用项目现有 GSAP，也可以用 Pixi ticker 插值。为了和其他页面动画统一，推荐 GSAP 只动画一个普通 camera 对象，在 `onUpdate` 中同步 Pixi container。

## 8. 地点精灵交互

Summer Town 中建筑悬停上浮可以在 Pixi 中等价实现：

```ts
// 伪代码
onHoverStart:
  tween(sprite, { y: baseY - 12, scale: 1.05 })
  showGlow()
  showLabel()

onHoverEnd:
  tween(sprite, { y: baseY, scale: 1 })
  hideGlow()
```

注意事项：

- 地图对象容器负责世界坐标，内部 sprite 才做 hover 位移，避免改变对象真实坐标。
- 建筑默认使用 `anchor = (0.5, 1)`，即底部中心落在地图坐标上。
- 点击命中区域和图片尺寸分开配置，透明 PNG 不应依赖整张矩形纹理命中。
- 开启 `sortableChildren`，默认可按 `zIndex` 排序；没有显式 zIndex 时可用 `y` 值排序。
- 拖拽阈值超过约 6 屏幕像素才视为移动，避免误触点击。

## 9. 编辑器与运行时复用

推荐拆成三层：

```text
map-domain/
├── map-document.ts       类型、版本、校验
├── map-migrations.ts     v2 → v3
├── map-selectors.ts      GameLocation + MapObject 合并
└── map-camera.ts         坐标、边界、聚焦计算

map-renderer/
├── PixiMapStage.tsx      纯舞台
├── MapObjectView.tsx
├── LocationObject.tsx
├── MapViewport.ts
└── asset-cache.ts

admin/maps/
├── ExplorationMapEditor.tsx
├── MapToolbar.tsx
├── LayerPanel.tsx
└── ObjectInspector.tsx
```

`PixiMapStage` 同时供编辑器和玩家运行时使用：

```tsx
<PixiMapStage
  document={document}
  locations={locations}
  mode="edit" // 或 "play"
  onObjectSelect={...}
  onObjectMove={...}
  onObjectActivate={...}
/>
```

两种模式只改变控制器和覆盖 UI，不复制渲染代码。

## 10. 推荐实施顺序

### 阶段 A：修正当前基础

1. `ExplorationPixiCanvas` 接收实际 `worldWidth/worldHeight`。
2. 增加地图平移、滚轮缩放、触控缩放和复位。
3. 将建筑锚点改为底部中心。
4. 增加 Y 排序和自定义 hit area。
5. 将乱码 UI 文本和 `editorData: any` 一并整理。

此阶段仍使用现有数据库字段，不做数据迁移。

### 阶段 B：引入 v3 地图文档

1. 定义 Zod schema 和 TypeScript 类型。
2. 实现旧百分比坐标到世界坐标的只读适配器。
3. 在 `editorData` 保存 layers 和 objects。
4. 增加迁移时双写，确保旧页面兼容。
5. 编辑器支持对象层级、锚点、缩放、旋转和锁定。

### 阶段 C：玩家运行时

1. 复用 PixiMapStage 建立探索页面。
2. 地点点击后聚焦并打开 React 详情卡。
3. 详情卡显示进入地点、可用房间、NPC 和任务。
4. 接入 `requiredOutputLevel/requiredFlags/disabled/hidden`。
5. 接入 BGM、环境音和地点音效。

### 阶段 D：环境细节

1. 装饰物和前景遮挡层。
2. 水波、闪光、云、船等低成本循环动画。
3. 时间或主题滤镜。
4. 导览路线和任务引导相机。
5. NPC 移动、碰撞或寻路；只有确有玩法需求时再引入。

## 11. 性能和资源约束

- 地图底图不要无限增大；大图优先 WebP/AVIF，必要时切片。
- 建筑透明图使用纹理图集时要注意最大纹理尺寸和移动端 GPU 限制。
- 使用 `Assets` 统一预加载，进入地图前加载底图和首屏地点，其余资源延迟加载。
- 静态装饰层可以缓存为纹理，避免每帧重复绘制。
- 只有真实动画对象进入 ticker；不要让每个静态地点都永久执行 `useTick`。
- 当前所有节点都在 `useTick` 中计算脉冲，建议仅在 hover/selected 时启动 tween。
- 监听 `webglcontextlost`，低端设备可以回退到简化效果，而不是维护另一套完整 DOM 地图。

## 12. 验收标准

第一版可按以下条件验收：

- 同一份地图数据可在后台编辑器和玩家探索页渲染。
- 地图尺寸来自 `GameMap.width/height`，不再写死。
- 旧地图未经人工修改即可正常加载。
- 鼠标、触屏均可平移和缩放。
- 点击与拖拽不会互相误判。
- 建筑支持透明 PNG、底部锚点、hover 上浮和独立命中区域。
- 点击建筑可平滑聚焦、打开详情并进入 Location/Room。
- 地图对象与 Location 业务数据分离，装饰物不污染导航模型。
- 隐藏、禁用和解锁条件在编辑器预览与正式运行时表现一致。

## 13. 最终建议

SpeakGuild 不应复制 Summer Town 的具体 DOM 实现，而应复制它的设计思想：

- 插画底图和可交互建筑分层；
- 用稳定的世界坐标组织内容；
- 相机移动整个世界，而不是逐个移动建筑；
- 建筑视觉、命中区域和业务入口分离；
- Canvas/Pixi 管高频世界交互，React 管业务 UI。

项目当前结构可以顺利组合这套设计。最安全的路径是保留 `GameMap/GameLocation/GameRoom`，先增强现有 `ExplorationPixiCanvas`，再通过有版本的 `editorData` 引入 MapObject，而不是立刻新增大量数据库表或改写全部地图数据。
