# SpeakGuild 英语剧情探索地图：产品、业务与素材调研

> 本文基于 Summer Town 文章、公开仓库源码和素材声明进行源码级调研，并结合 SpeakGuild 当前 Prisma 模型、剧情包、Ink、地图编辑器和练习记录提出产品方案。
>
> 结论分为两类：
>
> - **源码确认**：可以从公开代码和项目声明直接确认。
> - **产品建议**：结合 SpeakGuild 英语学习目标提出，不代表 Summer Town 原项目已有此能力。

## 1. 调研结论

Summer Town 是一个以氛围、地标故事和收藏为主的轻量互动网站。它没有复杂任务系统、账号系统、服务端存档或教育业务。其核心循环是：

```text
抵达小镇
  → 自由探索或自动导览
  → 打开地标
  → 阅读场景、故事和趣味事实
  → 收集地标印章
  → 在 Journal 中查看收藏进度
  → 继续探索其他地标或进入独立主题路线
```

SpeakGuild 不应直接复制这个业务循环，而应将其升级为：

```text
选择剧情包
  → 进入该剧情包的世界地图
  → 与角色接触并获得探索目标
  → 进入地点和房间
  → 点击物品发现英语
  → 听、看、说、使用词汇或句块
  → 与 NPC 完成剧情对话
  → 获得探索记录、收藏和剧情进度
  → 解锁下一房间、地点或章节
```

最值得借鉴的不是某个按钮，而是以下四点：

1. 把内容入口空间化，让用户感觉自己在“去一个地方”，而不是打开课程列表。
2. 给每个地点一致的故事卡结构，降低理解成本。
3. 用印章、护照和导览路线提供轻量进度反馈。
4. 通过视觉、文案、声音和微交互维持统一世界观。

## 2. Summer Town 的产品结构

### 2.1 首页地图

源码确认的功能：

- 首次会话显示约 1.45 秒的抵达动画。
- 用户可以选择“开始探索”或“乘渡轮导览”。
- 地图世界尺寸为 `2400 × 1680`。
- 支持拖拽平移、滚轮缩放和缩放按钮。
- 支持回到总览视角。
- 地图包含 14 个地标和一个独立码头热区。
- 地标可以按文化、美食、住宿、魔法、小岛分类筛选。
- 筛选后不匹配地标会降低透明度和饱和度。
- 建筑 hover 时上浮、放大并显示名称标签。
- 支持 `?place=<id>` 地标深链接。
- 点击地标后镜头聚焦，随后打开详情卡。
- 详情打开时地图导航栏收起，页面滚动被锁定。
- 地图闲置 8 秒后开始轻微漂移。
- 支持按预设路线自动游览四个地标。
- 支持白天、黄金时刻、星光三种主题。
- 支持声音开关；风铃岛和电台具有独立声音反馈。
- 尊重 `prefers-reduced-motion`。

### 2.2 地标详情卡

每个地标使用同一套内容结构：

```ts
interface Landmark {
  id: string;
  name: string;
  chip: string;
  filter: string;
  accent: string;
  whisper: string;
  tagline: string;
  lore: string;
  facts: Array<{ icon: string; text: string }>;
  img: string;
  scene: string;
  anchor: { x: number; y: number };
  zoom: number;
  w: number;
}
```

详情卡包含：

- 地标场景大图。
- 名称、分类和一句话标签。
- 世界观故事。
- 三条趣味事实。
- 收集印章按钮。
- 当前收藏数量提示。
- “下一个地标”入口。
- 特殊地标可进入独立路线页面。

这里值得借鉴的是“统一的内容卡契约”。即使地点主题不同，用户仍然知道去哪里找说明、事实、操作和下一步。

### 2.3 收藏和 Journal

源码确认：

- 地标印章使用 `localStorage` 保存。
- Journal 中的 Passport 展示 `n/14` 收藏进度。
- Passport 支持按地标类型过滤。
- 每张地标卡可以深链接回地图并直接打开地标。
- Journal 还包含小镇日历和明信片墙。
- 用户创建的明信片也只保存在 `localStorage`。

这些功能没有服务端业务和跨设备同步。它们更接近有反馈的内容展示。

### 2.4 独立主题路线

Windbell Isle 不是普通详情弹窗，而是一条滚动叙事路线：

```text
码头抵达
  → 铃兰草地
  → 风铃亭
  → 日落点
  → 灯塔
  → 结束段
```

它使用 GSAP ScrollTrigger、声音和局部交互，把一个特殊地点升级成“章节级体验”。

对 SpeakGuild 的启示是：普通地点用通用房间探索器；重要剧情地点可以拥有定制章节，但仍应通过同一剧情进度系统进入和结算。

### 2.5 Visit、日历和邮件表单

Visit 页面包含渡轮时刻、住宿、礼仪、打包清单和明信片等世界观内容。日历事件也是代码中的静态数据。邮件订阅表单只切换本地成功状态，没有实际后端提交。

这些页面的主要价值是加强“这个世界真实存在”的感觉，不应误判为成熟的旅游、日历或邮件业务。

## 3. Summer Town 的状态与业务边界

全局状态只有：

```ts
type TownState = {
  time: "day" | "golden" | "starlight";
  soundOn: boolean;
  stamps: string[];
  mapDetailOpen: boolean;
}
```

持久化也只有：

| 数据 | 存储 |
| --- | --- |
| 时间主题 | `localStorage` |
| 声音开关 | `localStorage` |
| 地标印章 | `localStorage` |
| 用户明信片 | `localStorage` |
| 是否看过加载动画 | `sessionStorage` |

它没有：

- 登录和用户账户。
- 数据库和服务端进度。
- 正式任务、奖励或解锁引擎。
- NPC 状态和关系。
- 房间级探索。
- 物品级交互。
- 学习目标和学习记录。
- 多设备同步。

因此 SpeakGuild 可以借鉴其体验结构，但业务模型必须以现有学习系统为主体。

## 4. 素材是如何生成和组织的

### 4.0 字体系统

Summer Town 的字体不是 AI 图片的一部分，而是通过 Google Fonts 加载的三套网页字体：

| 用途 | 字体 | 字重 |
| --- | --- | --- |
| 标题、地标名、按钮强调 | `Fredoka` | 500 / 600 / 700 |
| 正文、导航、标签和数据 | `Nunito` | 400 / 600 / 700 / 800 |
| 手写批注、明信片和氛围文案 | `Caveat` | 500 / 700 |

Tailwind 中的映射为：

```ts
fontFamily: {
  display: ["Fredoka", "Nunito", "sans-serif"],
  body: ["Nunito", "ui-sans-serif", "sans-serif"],
  hand: ["Caveat", "cursive"],
}
```

它显得协调的原因不是单独某一种字体，而是明确的角色分工：

- Fredoka 的圆润几何形状对应游戏标题和贴纸式 UI。
- Nunito 保持正文易读，同时不会显得过于商务。
- Caveat 只用于短句和批注，制造旅行手账感。
- 正文不使用 Caveat，避免长文本可读性下降。
- UI 普遍使用较粗字重、圆角、白色描边和柔和阴影，使字体与插画共享同一种视觉语言。

### 4.1 可以确认的生产过程

文章和仓库资料可以确认：

1. 早期曾用 Midjourney 尝试生成完整 2.5D 地图，但存在结构不合理、无法分层的问题。
2. 后来用 Cursor 搭载不同模型生成过初始网页版本。
3. 又尝试 Kimi K2.6 和 K3，结果逐步接近目标。
4. 最终网站版本主要通过 Kimi K3 Swarm 多代理方式迭代，下载时已是第 28 版。
5. 部署阶段又使用 Google AI 调整部署文件。
6. README 明确写明 vibe coding 工具为 Kimi K3 Swarm。
7. 仓库 NOTICE 明确说明：许多视觉资产使用 AI 图像生成工具制作，之后由维护者进行挑选、裁剪、排列和集成。
8. README 说明 `public/` 视觉素材不随源码使用 MIT 许可，不应直接复制到其他项目。

不能从公开资料确认的内容：

- 每一张最终图片具体由哪个图像模型生成。
- 完整提示词、seed、LoRA 或参考图参数。
- 每个素材经过了多少次 Photoshop 或其他人工修图。
- 最终底图是一次生成、局部重绘还是多图合成。

因此不能声称所有最终素材都由某一个明确模型直接生成。

### 4.2 资源分层

公开素材按用途组织得很清晰：

```text
public/
├── map-base.png              2400 × 1600 地图底图
├── map-base-ext.png          2400 × 1680 扩展地图底图
├── b-*.png                   各建筑透明切图
├── scene-*.png               地标详情场景图
├── i-*.png                   风铃岛独立建筑切图
├── isle-*-scene.png          风铃岛章节场景图
├── prop-boats.png            地图装饰物
├── ferry.png                 渡轮素材
├── logo.svg
└── cursor*.png/svg           定制光标
```

这相当于为一个地点准备两类视觉素材：

```text
地图上的建筑 cutout
        +
打开详情后的场景 illustration
```

这种双素材结构非常适合 SpeakGuild：

- 世界地图使用小型透明建筑图。
- 进入地点或房间后使用更高分辨率的场景图。
- 房间里的桌子、书本、杯子等再拆成可点击热区或独立物品图。

公开文件还能确认其资源规格经过标准化：

| 资源类型 | 实际常用文件规格 | 格式特征 |
| --- | --- | --- |
| 普通建筑 `b-*.png` | `1024 × 1024` | 32-bit RGBA 透明 PNG |
| 岛屿建筑 | `1024 × 1024` 或 `1024 × 1536` | RGBA 透明 PNG |
| 地标详情 `scene-*.png` | `1536 × 1024` | 不透明 RGB 场景图 |
| 岛屿横向章节场景 | `2048 × 1152` | 不透明 RGB 场景图 |
| 地图底图源文件 | `1536 × 1024` / `1536 × 1075` | 不透明 RGB |
| 道具 | 最高约 `1536 × 1024` | RGBA 透明 PNG |

代码中的世界坐标是 `2400 × 1680`，但底图源文件并非同像素尺寸；浏览器会把底图拉伸到逻辑世界尺寸。这说明“逻辑世界坐标”和“图片像素分辨率”是分开的。

所有普通建筑统一为 1024 方图且带 Alpha，可以合理推断作者至少执行了以下后处理：

1. 从候选生成图中选择建筑。
2. 移除背景或导出透明背景。
3. 清理边缘和残留像素。
4. 将建筑放入统一方形画布。
5. 保留一致安全边距。
6. 在代码中再用不同 `w` 值控制最终显示尺寸。

这是从文件结构和像素格式得出的制作流程推断，不是作者公开的逐步操作记录。

### 4.3 为什么早期整张 AI 地图难以交互

如果所有建筑都画死在一张图中，会出现：

- 建筑无法单独 hover、发光或上浮。
- 点击区域只能靠手工矩形覆盖。
- 无法改变前后遮挡关系。
- 无法按剧情隐藏、替换或损坏某座建筑。
- 同一建筑很难复用到其他地图。
- AI 生成的道路、透视和建筑逻辑错误难以单独修正。

Summer Town 的改进方向是将底图、建筑和装饰物拆开。SpeakGuild 应从一开始就采用这个生产标准。

## 5. SpeakGuild 的推荐产品定位

### 5.1 地图不是课程目录皮肤

如果地图只是把课程卡片换成建筑按钮，用户很快会把它理解成更慢的导航页。

地图必须提供列表页没有的价值：

- 空间线索：知道角色和事件在哪里发生。
- 自主发现：房间里存在非必点物品和隐藏内容。
- 情境记忆：单词和句块与具体房间、物品、角色绑定。
- 剧情状态：完成事件后环境、角色或物品发生变化。
- 路线选择：用户可以先探索，也可以接受角色引导。

### 5.2 三种进入模式

建议支持：

1. **剧情模式**：有明确目标和章节顺序，适合首次学习。
2. **自由探索**：已开放地点可随意进入，适合发现和复习。
3. **复习模式**：地图只高亮待复习词汇、未掌握物品和相关角色。

三种模式使用同一张地图和房间数据，只改变高亮、引导和结算规则。

## 6. 推荐核心循环

### 6.1 包级循环

```text
选择剧情包
  → 观看世界/章节简介
  → 进入剧情包地图
  → 查看当前任务和可探索地点
  → 完成若干地点与章节
  → 包级总结、奖励和复习入口
```

### 6.2 地图级循环

```text
NPC 或任务板给出线索
  → 高亮目标地点，但允许查看其他地点
  → 点击建筑
  → 相机聚焦
  → 地点卡展示角色、学习目标、发现进度
  → 进入地点
```

地点卡推荐字段：

- 地点名称和一句话世界观描述。
- 当前出现的角色。
- 本地点可发现内容 `3/8`。
- 关联剧情章节。
- 推荐英语等级。
- 当前任务目标。
- “进入”“稍后探索”“查看已发现内容”。

### 6.3 房间级循环

```text
进入房间
  → 环境语音/角色开场
  → 可点击物品出现轻量提示
  → 点击物品打开英语发现卡
  → 完成一个微学习动作
  → 物品标记为已发现或已掌握
  → 达成房间目标
  → 触发角色对话或剧情变化
  → 房间结算
```

### 6.4 章节级循环

```text
探索收集上下文
  → 与 NPC 进行 Ink 剧情对话
  → 使用本房间发现的词汇/句块
  → AI 判断目标、句块、语法和相关性
  → 通过后改变世界状态并解锁下一剧情节点
```

这可以直接复用当前 `StoryEpisode` 的：

- `vocabularies`
- `chunks`
- `sentencePatterns`
- `objectives`
- `minimumTurnCount`
- `requiredObjectiveCount`
- `requiredUsedChunkCount`
- `requiresRetell`
- `rewards`
- NPC 名称、角色和 persona
- Ink 脚本
- `StoryTurn` 与 `StoryRecord`

## 7. 物品点击后的英语体验

### 7.1 不要每次都弹同一种单词卡

物品类型不同，交互也应不同：

| 物品 | 推荐交互 |
| --- | --- |
| 可命名物品 | 单词、发音、图片、例句 |
| 容器/设备 | 动词搭配和操作指令 |
| 告示/菜单/书信 | 短文本阅读与信息提取 |
| 角色私人物品 | 剧情线索和推断 |
| 发声物品 | 听辨和跟读 |
| 多物品组合 | 方位、比较、数量和描述 |
| 任务物品 | 使用目标句块完成口语动作 |

### 7.2 英语发现卡

第一层应保持轻量：

```text
[物品图]
kettle
/ˈket.əl/  [播放]
水壶

The kettle is boiling.
[慢速播放] [跟读] [收藏]
```

展开后可以显示：

- 英文释义。
- 词性和音标。
- 常用搭配。
- 当前剧情中的例句。
- 相关句块。
- 角色语音。
- “用它说一句”按钮。

### 7.3 探索不等于掌握

建议将状态拆开：

```text
unseen
  → discovered       点击并看过
  → practiced        听过、跟读或答题
  → used_in_context  在对话中正确使用
  → mastered         达到复习策略要求
```

这样地图可以分别表达：

- 有闪光：尚未发现。
- 有小点：已发现但未练习。
- 有对勾：已完成当前房间要求。
- 有星标：已在剧情对话中使用。

### 7.4 微学习动作

每次点击控制在 5–20 秒：

- 点击播放标准发音。
- 选择正确物品名称。
- 听音后找物品。
- 跟读单词或短句。
- 用给定句块描述物品。
- 回答角色的情境问题。

复杂练习不要阻断每一个物品。房间中只选少量任务物品要求练习，其他物品允许轻量发现。

## 8. 角色如何进入地图系统

### 8.1 角色的三种空间状态

1. **地图角色**：站在地点外，提供线索或入口。
2. **房间角色**：出现在房间场景中，可点击对话。
3. **剧情角色**：进入 Ink/VN 对话，承担正式口语任务。

当前 `GameRoomNpc` 已能表达房间角色和基本日程：

- `characterId`
- `schedule`
- `defaultGreeting`
- `inkTalkScriptId`
- `sortOrder`

建议后续为角色放置增加：

- 房间坐标和锚点。
- 立绘/小人资源。
- 朝向和状态动画。
- 出现条件。
- 当前气泡提示。
- 与剧情章节的状态关联。

### 8.2 角色不应只是对话按钮

角色可以承担：

- 给出观察任务：“Find something we can use to boil water.”
- 对已发现物品发表评论。
- 在用户说错时提供世界内提示。
- 根据剧情进度更换位置和台词。
- 要求用户使用发现的词汇完成交际目标。
- 在章节结束后给出反馈和奖励。

## 9. 剧情包、地图和房间如何绑定

### 9.1 当前实际关系

当前系统中：

- `LearningPackage` 属于 `Scene`，并带版本和发布状态。
- `StoryEpisode` 也属于 `Scene`。
- `GameLocation` 可以通过 `sceneId` 关联 `Scene`。
- `GameMap` 目前没有 `sceneId` 外键，只有 `requiredChapterId` 字符串。
- `GameRoom` 可以绑定 `inkScriptId`。
- `ExplorationRecord` 已记录用户、角色、地点、房间、用户文本、NPC 回复和 Ink knot。

### 9.2 推荐权威关系

地图应绑定内容身份 `Scene`，不要绑定某个 `LearningPackage` 版本：

```text
Scene（剧情包内容身份）
├── LearningPackage v1/v2/v3（发布产物）
├── StoryEpisode[]
└── GameMap[]
    └── GameLocation[]
        └── GameRoom[]
```

原因：

- 包版本升级不应该复制一张新地图。
- 编辑中的地图应属于 Scene，而不是某个已发布 zip。
- 离线构建时再把当前地图文档和相关素材打入具体 LearningPackage 版本。

建议给 `GameMap` 增加可空 `sceneId` 外键。老地图可暂时不绑定。

### 9.3 StoryEpisode 与空间绑定

MVP 可以给 `StoryEpisode` 增加可空 `roomId`；但长期建议使用独立放置关系：

```ts
interface StoryEpisodePlacement {
  id: string;
  episodeId: string;
  mapId?: string;
  locationId?: string;
  roomId?: string;
  role: "start" | "main" | "complete" | "optional";
  sortOrder: number;
  requiredFlags?: Record<string, unknown>;
}
```

原因是一个章节可能：

- 在地图 NPC 处开始。
- 在咖啡店房间探索。
- 在另一个房间完成对话。
- 完成后回到地图角色处结算。

只在 `StoryEpisode` 上放一个 `roomId` 无法表达这条路线。

## 10. 房间物品数据模型

Summer Town 没有物品级业务，这部分需要 SpeakGuild 自己建立。

### 10.1 推荐实体

业务对象应存数据库，视觉位置存地图文档：

```text
ExplorationObject（业务）
        ↑ explorationObjectId
MapObject（视觉与命中区域）
```

推荐 Prisma 概念模型：

```prisma
model ExplorationObject {
  id             String   @id @default(cuid())
  roomId         String
  key            String
  displayName    String
  description    String?
  objectType     String
  assetUrl       String?
  interactionType String
  discoveryText  String?
  prompt         String?
  required       Boolean  @default(false)
  hidden         Boolean  @default(false)
  disabled       Boolean  @default(false)
  requiredFlags  Json?
  rewards        Json?
  sortOrder      Int      @default(0)
}

model ExplorationObjectVocabulary {
  objectId  String
  vocabId   String
  sortOrder Int @default(0)
}

model ExplorationObjectChunk {
  objectId  String
  chunkId   String
  sortOrder Int @default(0)
}

model ExplorationObjectPattern {
  objectId  String
  patternId String
  sortOrder Int @default(0)
}
```

视觉文档中的 MapObject 增加：

```ts
{
  type: "exploration_object",
  explorationObjectId: "...",
  transform: { x, y, width, height, anchorX, anchorY, zIndex },
  hitArea: { shape, points },
  interaction: { hoverEffect: "glow" }
}
```

### 10.2 为什么不把所有内容塞进 editorData

物品学习数据需要：

- 数据库外键完整性。
- 按词汇反查出现在哪些房间。
- 包构建和离线同步。
- 后台内容编辑。
- 用户学习记录和分析。
- 多语言文案。

因此坐标、旋转和命中区域可以放 `editorData`，但词汇、句块和任务关系应使用正式业务表。

## 11. 用户进度与记录

现有 `ExplorationRecord` 主要记录 NPC 对话，不足以记录物品发现。

推荐新增：

```prisma
model ExplorationObjectProgress {
  id               String   @id @default(cuid())
  userId           String
  objectId         String
  discoveredAt     DateTime?
  practicedAt      DateTime?
  usedInContextAt  DateTime?
  masteryState     String
  listenCount      Int      @default(0)
  practiceCount    Int      @default(0)
  bestScore        Float?
  lastResponse     String?
  metadata         Json?
  updatedAt        DateTime @updatedAt
}
```

并保留三个层次的进度：

```text
ObjectProgress   物品发现与练习
RoomProgress     房间发现率和任务完成
StoryRecord      正式剧情章节的口语通关
```

地图显示的是聚合结果，不应现场遍历所有原始练习记录。

## 12. 推荐业务状态机

### 12.1 物品

```text
hidden
  → available
  → discovered
  → practiced
  → completed
```

### 12.2 房间

```text
locked
  → available
  → entered
  → exploring
  → objective_ready
  → completed
  → replayable
```

### 12.3 剧情章节

```text
locked
  → available
  → active
  → awaiting_dialogue
  → passed / retry
  → completed
```

状态变化通过领域事件驱动：

```text
object.discovered
object.practiced
room.required_objects_completed
episode.started
episode.objective_completed
episode.passed
location.unlocked
reward.granted
```

不要把所有解锁判断写在 Pixi 点击事件里。Pixi 只发送 `activateObject(id)`，业务服务返回新的状态和展示结果。

## 13. 借鉴 Summer Town 后的页面功能

### 13.1 建议保留

- 抵达动画，但首次每个剧情包只播放一次。
- “自由探索”和“剧情导览”两个入口。
- 地图平移、缩放、聚焦和复位。
- 建筑 hover 上浮与标签。
- 地点详情卡。
- 自动导览路线，但路线来自剧情章节。
- 地点过滤器，但改成“主线、支线、角色、待复习、未发现”。
- 类似 Passport 的探索手册。
- 深链接到地图、地点和房间。
- 声音开关和 reduced motion。

### 13.2 应改造

| Summer Town | SpeakGuild |
| --- | --- |
| 收集地标印章 | 完成地点探索徽章 |
| 14 个固定地标 | 剧情包动态地点 |
| 地标 lore/facts | 地点故事、角色、学习目标 |
| Journal | 探索手册和词汇图鉴 |
| Ferry tour | 剧情导览/任务路线 |
| 静态 Calendar | 剧情事件和每日复习线索 |
| 明信片墙 | 学习者口语作品/剧情纪念卡 |
| 时间主题 | 剧情状态、时间或复习模式 |

### 13.3 暂时不要做

- 与学习目标无关的复杂天气系统。
- 大量纯装饰页面。
- 角色自由寻路。
- 实时多人地图。
- 每个地点完全定制一套渲染器。
- 为追求游戏感而强制所有物品都做题。

## 14. SpeakGuild 素材生产流程

### 14.1 先做剧情和空间设计

在生成图片前先产出：

```text
剧情包
├── 世界简介
├── 章节列表
├── 地点列表
├── 房间列表
├── 角色与日程
├── 每房间学习目标
├── 可点击物品清单
└── 视觉状态变化
```

图片不能先于空间数据，否则会再次陷入“图很好看，但无法分层和交互”。

### 14.2 建立视觉圣经

每个剧情包应有可复用的 Art Bible：

- 视角：正交、等距 2.5D 或正面房间。
- 摄像机高度和建筑朝向。
- 线条粗细。
- 主色、辅助色和阴影颜色。
- 材质和细节密度。
- 光照方向。
- 人物头身比。
- 禁止事项：文字、水印、复杂背景、错误透视等。
- 透明背景和安全边距规范。

### 14.3 推荐生产顺序

```text
1. 世界地图构图草案
2. 无交互建筑的底图
3. 独立建筑透明切图
4. 地点场景图
5. 房间背景图
6. 房间交互物品
7. 角色立绘/小人/表情
8. UI 图标、光标和装饰
9. 人工合成与一致性校验
10. 压缩、命名和上传
```

### 14.4 地图底图提示词结构

提示词应描述视觉规则，不要直接要求模型在图中写地名：

```text
用途：
  educational story exploration game world map

构图：
  isometric 2.5D illustrated campus town,
  fixed orthographic camera,
  clear roads and empty plots for interactive buildings

风格：
  soft hand-painted storybook,
  clean silhouettes,
  consistent outline weight,
  warm friendly palette

约束：
  no text, no labels, no watermark,
  no floating architecture,
  no duplicated roads,
  no interactive landmark buildings in the base layer
```

### 14.5 建筑素材提示词结构

```text
single [library] building,
same isometric camera and light direction as reference map,
storybook educational game asset,
clear readable silhouette,
transparent background,
ground contact at bottom center,
no people, no text, no shadow outside safe bounds
```

建筑应以底部中心为锚点，并保留自然接触阴影的独立控制能力。

### 14.6 房间场景与物品

房间背景图生成时要预留可点击区域：

```text
front-facing cozy library interior,
clear table, bookshelf, return desk and notice board,
objects separated with minimal overlap,
large readable shapes for mobile interaction,
no text, no people
```

如果物品会发生状态变化，应单独生成：

- 正常状态。
- hover/高亮可以由程序完成，不必生成。
- 已取走/打开/损坏等剧情状态。
- 必要时生成独立透明物品图和移除后的背景补片。

### 14.7 角色素材

同一角色需要统一：

- 身体比例和服装。
- 正面/侧面方向。
- 地图小人、房间半身像和 VN 立绘之间的识别特征。
- 常用表情集合。
- 命名规则和版本号。

角色素材应与 `GameCharacter` 和 expression 数据绑定，不要只写在剧情脚本文件名里。

### 14.8 人工 QA

每批素材至少检查：

- 透视是否统一。
- 光源方向是否统一。
- 建筑落地点是否合理。
- 透明边缘是否有白边或脏像素。
- 手机尺寸下物品是否可辨认。
- 点击区域是否与视觉匹配。
- 图中是否出现乱码文字。
- 角色手指、五官和重复物体是否异常。
- 与上一章节是否保持连续性。
- 是否符合商用和品牌使用规则。

## 15. 素材清单和 manifest

建议每个剧情包维护：

```ts
interface StoryWorldAssetManifest {
  version: number;
  sceneId: string;
  artBibleVersion: string;
  map: {
    background: AssetRef;
    thumbnail: AssetRef;
  };
  locations: Record<string, {
    mapSprite: AssetRef;
    detailScene: AssetRef;
    roomBackgrounds: Record<string, AssetRef>;
  }>;
  objects: Record<string, AssetRef>;
  characters: Record<string, {
    mapSprite?: AssetRef;
    roomSprite?: AssetRef;
    expressions?: Record<string, AssetRef>;
  }>;
}
```

每个 AssetRef 至少记录：

- 文件或 FileAsset ID。
- 原始尺寸。
- 用途。
- 生成工具和日期。
- 提示词版本或生成批次。
- 人工编辑说明。
- 许可/来源。
- 内容哈希。

这能避免后续无法判断一张图来自哪里、能否重生成或能否商用。

## 16. 内容生产工作流

推荐后台生产顺序：

```text
创建 Scene / 剧情包
  → 创建 StoryEpisode 和学习目标
  → 创建角色
  → 创建 GameMap / Location / Room
  → 将 Episode 放置到空间路线
  → 为房间创建 ExplorationObject
  → 绑定词汇、句块和句型
  → 生成并上传地图、房间、物品和角色素材
  → 在 Pixi 编辑器放置并绘制命中区域
  → 预览剧情模式和自由探索模式
  → 校验解锁与学习记录
  → 构建 LearningPackage
```

包构建时应包含：

- 地图文档。
- Location、Room 和 ExplorationObject 数据。
- StoryEpisode、Ink 和学习内容。
- 角色资源。
- 地图、房间、物品图片和音频。
- 初始解锁状态。
- 资源 manifest 和版本。

## 17. MVP 范围

第一版建议只做一个剧情包：

- 1 张地图。
- 3 个地点。
- 每地点 1–2 个房间。
- 2–3 个角色。
- 每房间 5–8 个可点击物品。
- 每房间 2 个必做物品，其余自由发现。
- 2–3 个 StoryEpisode。
- 地图、房间、物品三层进度。
- 词汇卡、播放、跟读和一句话口语任务。
- 章节对话复用现有 Ink/VN 与 AI 评价。

验收重点不是物品数量，而是完整闭环：

```text
发现物品
  → 学到表达
  → 在 NPC 对话中使用
  → 系统识别使用成功
  → 世界状态和剧情进度变化
```

## 18. 推荐开发顺序

### 阶段 1：空间绑定

- 给 GameMap 增加可空 `sceneId`。
- 定义 StoryEpisodePlacement。
- 完成 Scene → Map → Location → Room → Episode 查询。

### 阶段 2：物品探索

- 新增 ExplorationObject 及内容关系。
- 在房间编辑器中放置物品和 hit area。
- 实现物品英语发现卡。
- 新增 ObjectProgress。

### 阶段 3：学习闭环

- 将房间已发现词汇注入 Ink/VN 练习上下文。
- AI 评价用户是否使用目标词汇和句块。
- 章节通过后更新房间、地点和地图状态。

### 阶段 4：内容生产

- 建立 Art Bible 和素材 manifest。
- 提供地图/建筑/房间/物品生成模板。
- 将素材检查加入剧情包发布流程。

### 阶段 5：体验增强

- 剧情导览相机。
- 探索手册和词汇图鉴。
- 角色地图状态和轻量日程。
- 环境音、时间变化和章节视觉变化。

## 19. 最终建议

Summer Town 证明了“底图 + 独立建筑 + 相机 + 统一故事卡 + 收藏进度”足以让静态插画产生探索感。

SpeakGuild 应在这套体验骨架上加入真正的学习业务：

```text
空间是上下文
物品是词汇入口
角色是交际入口
剧情是使用动机
练习记录是进度依据
世界变化是学习反馈
```

技术上继续使用 PixiJS + React；数据上以 Scene 作为剧情世界身份，以 GameMap/Location/Room 表达空间，以 StoryEpisode 表达正式剧情任务，以 ExplorationObject 表达房间物品，以现有词汇、句块、句型和 AI 对话评价完成学习闭环。
