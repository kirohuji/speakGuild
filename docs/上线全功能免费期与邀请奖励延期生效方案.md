# 上线全功能免费期与邀请奖励延期生效方案（最小实现）

> **状态**：设计稿，尚未实施  
> **目标**：上线初期，所有登录用户无需开会员即可使用完整功能；邀请仍送 5 天会员，但免费期内只累计、不立即开始计算，免费期结束后再统一发放。  
> **原则**：复用现有的系统配置、会员表和邀请表；不新增活动系统、权益账本、定时任务或复杂订阅接续逻辑。

---

## 1. 最终方案

只增加两类很小的改动：

1. 在现有后台增加一个“上线全功能免费期”开关。开关保持开启期间，所有登录用户直接按会员权限放行；等运营确认要收费时，再手动点击“结束免费期”。
2. 在现有 `Referral` 邀请记录上增加“本次奖励天数”和“是否已发放”两个字段。免费期内邀请成功时只记下 5 天；免费期结束后由管理员在后台点击一次“结算邀请会员奖励”，批量把这些天数叠加到用户现有会员到期日。

这足够解决当前问题：

- 免费期内每个人都能完整使用；
- 邀请奖励不会在免费期白白消耗；
- 同一个邀请不会重复发；
- 不改变现有支付、会员、邀请积分的主体逻辑。

不需要给所有用户创建会员记录，也不需要新增复杂的“活动”“奖励钱包”“自动续期”等系统。

---

## 2. 规则定义

### 2.1 免费期的判定

后台只保留以下两个值：

| 配置键 | 示例值 | 说明 |
|---|---|---|
| `launch_free_access_enabled` | `true` | 是否启用本次上线免费期 |
| `launch_free_access_ended_at` | `2026-09-30T23:59:59+08:00` | 实际结束时间；开始时为空，由“结束免费期”操作自动写入 |

统一规则：

```text
免费期有效 = enabled 为 true
```

因此免费期可以持续任意长时间，运营可随时调整产品、内容和成本，不需要预先承诺结束日期。点击“结束免费期”后，后端在同一事务内把 `enabled` 改为 `false`，并把当前服务器时间写入 `ended_at`。该时间不允许手工修改，它是邀请奖励的统一起算点和客服核对依据。

### 2.2 免费期内开放什么

“全功能免费”就是按正式会员放行：完整学习包、剧情/练习内容、表达库容量及 AI 功能。

AI 在免费期也直接按会员逻辑放行，即不限每日对话/复盘次数；但原有 API 限流、登录校验和异常风控继续生效。若后续成本过高，再单独调低免费期 AI 配额；首期不为此增加活动配额体系。

### 2.3 邀请奖励规则

- 邀请人：立即获得现有的 `+100` 积分。
- 被邀请人：立即获得现有的 `+50` 积分。
- 邀请人的 5 天会员：
  - 免费期**进行中**：只记录“待发 5 天”，不修改 `UserMembership.expiredAt`；
  - 免费期**结束后**：按现在的逻辑立即叠加到会员到期日。
- 多成功邀请 1 人，就多累计 5 天。

免费期结束后结算时，奖励按下面方式计算：

```text
新到期日 = max(当前会员到期日, 实际免费期结束时间) + 待发奖励天数
```

例如运营在 9 月 30 日点击结束免费期，用户在此期间邀请 3 人：

- 用户没有会员：结算后获得 15 天，从 9 月 30 日开始算；
- 用户已有会员至 10 月 20 日：结算后到期日为 11 月 4 日，不会覆盖现有会员。

这个方案只适合当前“首期免费、同时关闭购买”的场景。免费期内不建议让用户购买，否则 RevenueCat 的订阅同步可能更新 `expiredAt`；首期直接隐藏购买入口即可规避该复杂情况。

## 3. 需要改动的数据

### 3.1 复用 `system_config`

在现有 `system_config` 中增加两条配置：

```ts
{ key: 'launch_free_access_enabled', value: 'false', group: 'feature', label: '上线全功能免费期', type: 'boolean' }
{ key: 'launch_free_access_ended_at', value: '', group: 'feature', label: '免费期实际结束时间', type: 'string' }
```

`launch_free_access_ended_at` 不是运营手填项。它由一个很小的“结束免费期”后台接口自动写入 ISO 时间，例如 `2026-09-30T23:59:59+08:00`；后台只读展示即可。这样不需要日期选择器，也不会因手动填错时间导致奖励计算出错。

### 3.2 只给 `Referral` 增加两个字段

```prisma
model Referral {
  // 已有字段省略
  membershipRewardDays      Int       @default(0) // 本次邀请承诺的会员天数
  membershipRewardGrantedAt DateTime?              // 批量结算成功的时间；为空即待发
}
```

含义很简单：

- `membershipRewardDays = 5`、`membershipRewardGrantedAt = null`：这次邀请的 5 天还没发；
- `membershipRewardGrantedAt` 有值：已经结算过，不能再次结算。

不新建奖励表，不改 `UserMembership` 表。`Referral.referredUserId` 本身唯一，邀请关系不会重复；再用 `membershipRewardGrantedAt` 标记发放完成，就能保证结算接口可重复点击而不重复送天数。

## 4. 少量代码调整

### 4.1 一个轻量的免费期判断方法

新增一个很小的公共方法（可放在现有会员模块或 common 下），只负责读取上面两个配置并返回 `true / false`：

```ts
isLaunchFreeAccessActive(): Promise<boolean>
```

不需要新建复杂的 `EntitlementService`。下列现有位置调用这个方法即可：

| 现有位置 | 改动 |
|---|---|
| `AiQuotaService` | 免费期有效时直接放行，返回无限配额 |
| `LearningService` | 免费期有效时允许下载/访问非免费学习包 |
| 其他明确的会员功能判断 | 在现有 `isMember` 前加 `isLaunchFreeAccessActive()` |
| `MembershipService.getCurrentMembership` | 返回“上线全功能体验期”状态和结束时间，供前端展示 |

实施时用 `rg` 再扫一次 `userMembership`、`isMember`、`expiredAt`，把真正的服务端限制点都接上；不能只打开现有的 `learning_pack_free_downloads_enabled`，因为它只影响学习包下载，不影响 AI 配额等功能。

### 4.2 改邀请发奖逻辑

现有 `ReferralService.applyReferral` 会调用 `grantTrialDays`，立即修改 `UserMembership.expiredAt`。改为：

```text
邀请成功
  → 创建 Referral，membershipRewardDays = 当前 invite_trial_days（默认 5）
  → 正常发放双方积分
  → 若免费期未结束：不调用 grantTrialDays
  → 若免费期已结束：按原逻辑立即调用 grantTrialDays，随后写 membershipRewardGrantedAt
```

免费期内的通知文案改为：

> 你邀请的好友已完成注册，100 积分已到账；5 天会员奖励已累计，将在全功能免费期结束后自动发放。

### 4.3 增加一个管理员结算接口

新增一个仅管理员可调用的接口，例如：

```text
POST /admin/referral/settle-launch-rewards
```

接口逻辑：

1. 读取 `launch_free_access_ended_at`；为空则拒绝执行，说明免费期尚未结束。
2. 找出所有 `membershipRewardDays > 0` 且 `membershipRewardGrantedAt IS NULL` 的邀请记录。
3. 对每条记录按现有 `grantTrialDays` 的叠加方式给邀请人加天数；结算基准取 `max(会员到期日, 实际免费期结束时间)`。
4. 在同一个数据库事务中写入 `membershipRewardGrantedAt = now`。
5. 返回本次结算的邀请条数、用户数和总天数。

每条邀请都在事务中完成“加天数 + 标记已发”，所以接口可以安全重试。建议一次处理 100 条，循环直到结束；首期用户量小，也可直接一次处理。

不做自动定时任务：运营先点击“结束免费期”，再点击一次“结算”。为了不漏操作，结束成功后后台直接显示“有 N 笔邀请会员奖励待结算”提示，并提供结算按钮。

### 4.4 增加一个“结束免费期”后台操作

不能只让管理员把 `launch_free_access_enabled` 从 `true` 改成 `false`，因为系统还需要准确记住奖励从哪一刻开始计算。因此增加一个非常小的管理员接口，例如：

```text
POST /admin/system-config/end-launch-free-access
```

接口只做三件事，并使用一次事务完成：

1. 校验当前免费期开关确实为开启状态；
2. 写入 `launch_free_access_enabled = false`；
3. 若 `launch_free_access_ended_at` 为空，写入当前服务器时间。

后台按钮文案为“结束全功能免费期并进入奖励结算”，点击前二次确认：`结束后普通用户将恢复免费版限制，确认继续？`。成功后显示实际结束时间和“结算邀请奖励”按钮。

### 4.5 关闭购买

免费期有效时：

- 前端会员页显示“全功能体验期至 X 月 X 日”，隐藏购买按钮；
- 后端创建订单接口也校验免费期，直接返回“当前为全功能免费期，无需购买”；
- `POST /auth/promo-trial` 返回“当前免费期内，无需领取试用”。

这是防止用户在免费期付费、又因订阅回调和邀请奖励混合而产生额外复杂度的关键。恢复收费时只需把 `launch_free_access_enabled` 关闭，不需要数据迁移。

## 5. 后台操作流程

### 开始前

1. 在“系统设置 → 功能开关”中开启“上线全功能免费期”。
2. 确认“免费期实际结束时间”为空（新一轮免费期必须为空）。
3. 保持 `invite_trial_days = 5`。
4. 发布前检查会员页已隐藏购买、试用领取已禁用。

### 免费期中

- 不需要人工发放会员；邀请成功会自动累计待发天数。
- 后台可按 `Referral` 中未结算记录统计待发天数；如暂不做统计页面，先用数据库查询即可。
- 免费期无需设置截止日；你可以一直保持开启，直到产品和运营都准备好收费。
- 若误操作结束免费期，不建议直接重新打开，应先确认是否已经结算奖励；首期由管理员人工处理即可，避免用户权益重复计算。

### 免费期结束后

1. 在后台点击“结束全功能免费期并进入奖励结算”，确认实际结束时间已写入。
2. 在后台点击“结算邀请会员奖励”。
3. 核对返回的“结算人数 / 总天数”，必要时重复点击；已结算记录会自动跳过。
4. 恢复购买页和新人试用（若仍需要新人试用）。

## 6. 前端最小展示调整

不需要新增复杂页面，只改两处文案：

- **会员页**：免费期内显示 `全功能体验期进行中，至 X 月 X 日结束`，不显示会员购买卡片。
- **邀请页**：总奖励可以继续显示累计天数；增加一行 `其中 N 天将在免费期结束后发放`。邀请明细可用 `membershipRewardGrantedAt` 区分“待发放 / 已发放”。

免费期结束且结算完成后，页面自动恢复现有会员展示即可。

## 7. 验收清单

- [ ] 未开启免费期时，现有免费/会员逻辑完全不变。
- [ ] 免费期内，普通登录用户可使用学习包、AI 和其他所有会员功能。
- [ ] 免费期内，邀请积分立即到账，但 `UserMembership.expiredAt` 不会因邀请改变。
- [ ] 每条成功邀请都记录 5 天待发奖励；多次邀请可累计。
- [ ] 点击结束免费期时，系统准确保存一次实际结束时间；重复点击不会覆盖该时间。
- [ ] 免费期结束后结算一次，用户到期日从“原到期日”和“实际免费期结束时间”中较晚者开始叠加。
- [ ] 结算接口重复调用不会重复赠送。
- [ ] 免费期内不能创建购买订单，也不能领取新人试用。
- [ ] 结束免费期并完成结算后，购买、试用和原会员逻辑恢复正常。

## 8. 本次明确不做的事

为保持上线简单，本次不做以下能力：

- 不新增运营活动管理系统；
- 不新增会员奖励钱包或奖励流水表；
- 不做免费期结束自动定时结算；
- 不处理“免费期内购买后赠送天数与自动续订完全无缝接续”的复杂场景；
- 不做老会员冻结订阅、按天自动补偿。

首期上线阶段，上述能力都不是必须。等免费期结束、开始真实收费，并确认有持续的运营活动需求后，再把这套最小方案演进为完整活动系统即可。
