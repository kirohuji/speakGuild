# 文件资源生命周期

## 设计目标

文件资源采用一个简单的两层模型：`FileAsset` 保存对象存储元数据，业务表外键或 `FileReference` 表示资源正在被使用。不存在手工维护的引用计数，也不存在可绕过引用检查的强制删除。

必须始终满足以下约束：

1. 业务数据与资源引用在同一个数据库事务中写入或移除。
2. 所有结构化资源外键使用 `ON DELETE RESTRICT`，数据库是最后一道安全屏障。
3. 上传成功但尚未被业务保存的资源允许暂时闲置，由维护任务延迟处理。
4. 清理必须先检查、再由管理员确认，并在真正删除前重新检查。
5. 清理顺序固定为：记录删除凭据并删除 `FileAsset`（同一事务）→ 删除 COS 对象 → 标记物理删除完成。
6. COS 删除失败时保留 `FileAssetPurge`，后续清理任务自动重试。允许短期残留对象，不允许出现业务仍引用但对象已丢失。

## 管理流程

资源管理页的“检查未使用资源”会向后台任务中心提交 `file-asset-inspect`。检查只返回超过保留期、没有外键引用、没有 `FileReference`、也未在受支持内容字段中出现的候选资源。

管理员确认后提交 `file-asset-cleanup`。任务不会直接信任上一次检查结果，而会逐项重新检查；检查期间新产生引用的资源会被保留。任务结果和失败详情可在任务中心查看。

## 开发约束

- 长期保存资源时只保存资源 ID 或 `asset://<id>`，不要持久化 COS 签名 URL。
- 新增包含资源 ID 的 JSON/文本字段时，保存接口必须同步对应的 `FileReference`；同时把表加入维护服务的保守内容检查范围，直到该字段改为真实外键。
- 不要在表单移除文件时调用后端删除引用。只更新本地表单，最终由业务保存事务统一同步。
- 不要直接删除 COS 对象。业务代码只解除引用；物理清理由资源维护任务负责。
- 离线包更新先写入并验证新文件，再切换清单，最后回收旧文件。中断时可以留下缓存垃圾，但不能先删除当前可用资源。

## 运维检查

- 定期查看任务中心中 `file-asset-cleanup` 的失败项。
- `FileAssetPurge.status = failed` 表示数据库已经安全解除资源、COS 删除待重试，不代表线上内容丢失。
- 若需扩大扫描范围，优先增加真实外键或同步 `FileReference`，不要重新引入 `refCount`、资源状态机或定时强制删除。
