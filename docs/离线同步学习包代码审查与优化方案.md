## 二、核心问题清单

### 2.1 🔴 严重问题

#### 2.1.1 同步路径不统一——两套 Sync 机制并存

**现状：**

| 数据类型 | 同步方式 | 入口 |
|----------|----------|------|
| warmup_records | outbox → `POST /sync/push` | `syncOutbox.enqueue()` → `offlineSyncService.flush()` |
| daily_practice (run + attempt) | 直接调 `dailyPracticeApi.complete()` | `daily-practice.repository.ts` 直接 HTTP |
| practice_session / practice_turn | outbox + 尝试立即 HTTP | `practiceRepository.submitTurn()` |
| expression (word/chunk/pattern) | outbox → `/sync/push` 批量 | `offlineSyncService.flush()` |
| my_unit (enroll/quit) | outbox → `/sync/push` 批量 | `offlineSyncService.flush()` |

**问题：**
- `daily_practice` 不走 outbox，意味着如果用户离线完成今日任务，数据**永远不会自动同步**，必须等到下次在线时手动触发。
- `practiceRepository.submitTurn()` 先写 outbox，然后**立即尝试 HTTP**；如果 HTTP 失败，outbox 保留，但错误被静默吞掉（`catch { /* The outbox keeps the turn for later replay */ }`）。
- 两条路径的失败重试策略完全不同：outbox 有 `retryCount` + permanent error 判断；直接 HTTP 没有。

**建议：**
> 全部用户产生的写操作统一走 outbox → `flush()` 模型。`daily_practice` 的 `complete()` 调用也应入队 outbox，由 `offlineSyncService.flush()` 统一处理。

```ts
// 统一模型
async function submitUserData(type, payload) {
  // 1. 先写本地 SQLite（即时反馈）
  await localRepo.save(type, payload)
  // 2. 入队 outbox（延迟同步）
  await syncOutbox.enqueue({ entityType: type, ... })
  // 3. 如果在线，尝试立即 flush（可选，非阻塞）
  if (navigator.onLine) offlineSyncService.flush().catch(() => {})
}
```

#### 2.1.2 学习包安装 `installUnitFromZip` 方法过长（~450行）

**文件：** `learning-pack.service.ts:407-860`

**问题：**
- 单一方法包含：zip 解压、manifest 解析、topic 读取、内容索引写入、asset SHA256 校验、文件系统写入、引用计数更新、安装记录持久化
- 如果中途失败（如第 8 步资源提取失败），前面已写入的 SQLite 数据（第 6-7 步）**没有回滚**
- 进度回调 `report()` 和 console.log 散落各处，难以单独测试

**建议：**
> 拆分为独立的小方法，每个方法有明确的输入/输出和错误边界：

```ts
class LearningPackInstaller {
  async install(unitId: string, onProgress, signal): Promise<InstalledLearningPack> {
    // ① 下载 zip
    const zipBuffer = await this.downloadZip(unitId, signal)
    // ② 解析 manifest + checksums
    const { manifest, checksums, entries } = await this.parseZip(zipBuffer)
    // ③ 读取并校验内容 JSON
    const { unitDetail, topicDetails } = await this.readContent(entries, checksums, manifest)
    // ④ 写入 SQLite 内容（含 installing 状态标记）
    await this.persistContent(manifest, unitDetail, topicDetails)
    // ⑤ 提取并写入资源文件
    await this.extractAssets(manifest, entries, checksums, onProgress, signal)
    // ⑥ 标记安装完成
    return await this.finalizeInstall(manifest)
  }
}
```

#### 2.1.3 `asset_refs` 全表扫描性能问题

**文件：** `learning-pack.service.ts:568-573`

```ts
// 一次性加载所有 asset_refs 到内存 Map
const allRefsList = await localDb.list<any>('asset_refs')
const refsBySha256 = new Map<string, any>()
for (const ref of allRefsList) {
  if (ref.sha256) refsBySha256.set(ref.sha256, ref)
}
```

**问题：**
- 每次安装学习包都全量加载 `asset_refs` 到内存。当用户安装了 10+ 个包（每个包 50-200 个资源），这个 Map 可能包含数千条记录。
- 同一次安装中，`asset_refs` 还被多次全表扫描（installDelta 里有 3 次 `localDb.list('asset_refs')`）

**建议：**
> 利用已有索引 `idx_asset_refs_sha256`，改为按 SHA256 精确查询：

```ts
async function hasAssetRef(sha256: string): Promise<boolean> {
  const refs = await localDb.findByIndex('asset_refs', 'sha256', sha256)
  return refs.length > 0
}
```

这样每次只查询需要的 SHA256，而不是全表扫描。如果批量查询多，可以用 `findByIndexIn`：

```ts
const existingRefs = await localDb.findByIndexIn('asset_refs', 'sha256', sha256List)
const existingShas = new Set(existingRefs.map(r => r.sha256))
```

#### 2.1.4 后端 `sync.pull` 游标设计缺陷

**文件：** `apps/backend/src/modules/sync/sync.service.ts:390-430`

```ts
// 计算下一页 cursor：取所有返回记录中最大的时间戳
const timestamps: number[] = [];
for (const e of expressionItems) timestamps.push(e.updatedAt.getTime());
// ...
const nextCursor = timestamps.length > 0
  ? new Date(Math.max(...timestamps)).toISOString()
  : new Date().toISOString();
```

**问题：**
- 取所有类型记录的 `max(updatedAt)` 作为统一 cursor。假如 `expressionItems` 最新时间是 T1，`practiceSessions` 最新时间是 T2（T2 > T1），cursor 设为 T2。
- 下一次 pull 用 `updatedAt > T2`，会**漏掉**在 T1 和 T2 之间更新的 `expressionItems`（因为上次只返回了 ≤ T1 的 expression，而 > T1 且 ≤ T2 的被跳过了）。
- 这是一个**经典的分页游标 bug**：不能用全局 max cursor 来分页不同类型的数据。

**建议：**
> 改为每种类型独立 cursor：

```ts
// Request
{ cursors: { expressionItems: "2026-01-01T00:00:00Z", sceneProgresses: "2026-01-01T00:00:00Z", ... } }

// Response
{ cursors: { expressionItems: "2026-01-02T00:00:00Z", sceneProgresses: "2026-01-01T00:00:00Z", ... }, hasMore: { expressionItems: true, sceneProgresses: false, ... } }
```

或者更简单的方案：将不同类型的数据拆分到独立接口，各自维护 cursor。

### 2.2 🟡 中等问题

#### 2.2.1 安装失败无回滚机制

**文件：** `learning-pack.service.ts`

**现状：**
- 安装开始时写入 `status: 'installing'` 到 `downloaded_packs`
- 逐步写入 `downloaded_unit_details`、`ink_scripts`、`offline_vocabularies`、`offline_chunks`、`offline_patterns`、`offline_content_refs`、`asset_refs`
- 如果中途失败（如资源提取阶段），前面写入的 SQLite 数据**残留**在数据库中
- 下次重新下载时，这些残留数据可能导致去重逻辑误判（认为内容已存在）

**建议：**
> 引入安装事务标记：

```ts
// 安装开始：记录 installing 状态 + 安装开始时间
await localDb.put('downloaded_packs', { ...pack, status: 'installing', installStartedAt: now })

// 安装失败/取消：清理本包写入的所有数据
async rollbackInstall(packId: string) {
  await localDb.delete('downloaded_packs', packId)
  await learningContentRepository.removePackContentIndex(packId)
  await localDb.deleteWhere('downloaded_unit_details', item => item.unitId === packId)
  await localDb.deleteWhere('ink_scripts', item => item.unitId === packId)
  await localDb.deleteWhere('asset_refs', item => item.packId === packId)
}
```

#### 2.2.2 `syncOutbox.markSynced()` 直接删除记录——无法审计

**文件：** `sync-outbox.ts:67-72`

```ts
async markSynced(id: string): Promise<void> {
  try {
    await localDb.delete('outbox', id)
  } catch (error) {
    console.warn('[sync-outbox] markSynced delete failed:', error)
  }
}
```

**问题：**
- 同步成功后立即删除，没有任何记录保留。如果出现"服务端说 synced 但实际数据丢失"的情况，无法追溯。
- `markFailed` 保留记录但 `markSynced` 删除，不对称。

**建议：**
> 改为标记状态 + 定期清理，而非立即删除：

```ts
async markSynced(id: string): Promise<void> {
  const item = await localDb.get('outbox', id)
  if (!item) return
  await localDb.put('outbox', { ...item, status: 'synced', syncedAt: new Date().toISOString() })
}
```

然后在 `cleanup()` 中统一清理 7 天前的 synced 记录。当前 `cleanup()` 已经在做这件事，但 `markSynced` 没有给它机会。

#### 2.2.3 `MAX_PULL_PAGES = 5` 硬限制可能丢数据

**文件：** `offline-sync.service.ts:410-423`

```ts
const MAX_PULL_PAGES = 5
// ...
if (pages >= MAX_PULL_PAGES) {
  console.warn(`[offline-sync] pull reached max pages (${MAX_PULL_PAGES}), remaining data will be pulled on next sync`)
  break
}
```

**问题：**
- 每页 500 条 × 5 页 = 最多 2500 条变更。对于首次同步或长时间未同步的用户，可能不够。
- 如果 `hasMore` 仍为 true 但被截断，cursor 已更新到最新，剩余数据**永远不会被拉取**（因为下次 sync 时 cursor 已跳过这些数据）。

**建议：**
> 去掉硬限制，改为基于时间的保护：

```ts
const MAX_SYNC_DURATION_MS = 30_000 // 单次 pull 最长执行 30 秒
const startedAt = Date.now()
while (result.hasMore) {
  if (Date.now() - startedAt > MAX_SYNC_DURATION_MS) {
    // 不更新 cursor，下次从同一位置继续
    console.warn('[offline-sync] pull timeout, will resume on next sync')
    return { cursor, changed: totalChanged, deleted: totalDeleted }
  }
  // ...继续拉取
}
```

关键区别：**超时时不更新 cursor**，下次从同一位置继续。

#### 2.2.5 日志系统不一致

**问题：**
- `learning-pack.service.ts` 使用 `console.log` 带 `[learning-pack]` 前缀 + 性能计时器
- `offline-sync.service.ts` 使用 `console.warn` 零星打印
- `learning.store.ts` 使用 `console.log` 带 `[learning-store]` 前缀 + emoji
- `practice.repository.ts` 使用 `console.log` 带 `[practiceRepo]` 前缀
- 没有统一的日志级别控制（debug/release）

**建议：**
> 引入简单的 logger wrapper，支持静默模式：

```ts
// lib/logger.ts
const LOG_LEVELS = { debug: 0, info: 1, warn: 2, error: 3 } as const
type LogLevel = keyof typeof LOG_LEVELS
const currentLevel: LogLevel = __DEV__ ? 'debug' : 'warn'

export function createLogger(scope: string) {
  return {
    debug: (msg: string, data?: unknown) => { if (LOG_LEVELS[currentLevel] <= 0) console.log(`[${scope}]`, msg, data ?? '') },
    info:  (msg: string, data?: unknown) => { if (LOG_LEVELS[currentLevel] <= 1) console.log(`[${scope}]`, msg, data ?? '') },
    warn:  (msg: string, data?: unknown) => { if (LOG_LEVELS[currentLevel] <= 2) console.warn(`[${scope}]`, msg, data ?? '') },
    error: (msg: string, data?: unknown) => { if (LOG_LEVELS[currentLevel] <= 3) console.error(`[${scope}]`, msg, data ?? '') },
  }
}
```

### 2.3 🟢 建议优化

#### 2.3.1 类型安全——大量 `any` 类型

**分布：**
- `learning-pack.service.ts`: `unitDetail: any`, `topicDetail: any`, `asset: any` (50+ 处)
- `offline-sync.service.ts`: `item: any`, `payload: any` (80+ 处)
- `learning.repository.ts`: `unitDetail: any`, `topicDetails: any[]`

**建议：**
> 为关键数据结构定义接口，放在 `lib/offline/types.ts` 中：

```ts
// lib/offline/types.ts
export interface OfflineUnitDetail {

export interface OfflineTopicDetail {

  // ...
```

#### 2.3.2 SQLite Schema 混用两种存储模式

**现状：**

| 表名 | 模式 | 示例 |
|------|------|------|
| `downloaded_packs` | 混合：`pack_id`, `status`, `version` 独立列 + `data TEXT` | 查询快，但 manifest 存两份（列 + data 内的 JSON） |
| `warmup_record_entries` | 混合：`record_id`, `step_id` 独立列 + `data TEXT` | 索引友好 |
| `kv` | 纯 JSON：只有 `id`, `data`, `updated_at` | 灵活性高 |
| `my_learning_units` | 纯 JSON：只有 `id`, `data`, `updated_at` | 但每次读取都要 parse 整个 JSON |

**建议：**
> 统一为混合模式：高频查询字段（用于 WHERE/INDEX）独立列，其余放 `data JSON`。

当前 `downloaded_packs` 的问题是 `data` 列包含了 `manifest`（完整的 LearningPackManifest JSON），而 `pack_id`、`version`、`title` 又在独立列中**重复存储**。应该：

- `pack_id`, `version`, `status`, `title`, `installed_at` → 独立列（用于索引查询）
- `manifest` → 仅存储在 `data` JSON 中（不重复）

#### 2.3.5 下载完成后的 3 秒延迟清除是反模式

**文件：** `learning.store.ts:414` 和 `learning.store.ts:782`

```ts
setTimeout(() => {
  set((s) => ({
    downloadTasks: s.downloadTasks.filter((t) => t.packId !== next.packId || t.status !== 'done'),
  }))
}, 3000)
```

**问题：**
- 如果用户在 3 秒内关闭 App，下次打开时 `done` 状态的任务仍在列表中（因为 `readPersistedPackTasks()` 会恢复）
- setTimeout 在后台可能不执行（移动端 WebView 被挂起）

**建议：**
> 将 `done` 状态的任务在持久化时过滤掉（`persistPackTasks` 已实现），同时在恢复任务时过滤：

```ts
function readPersistedPackTasks(): DownloadTask[] {
  // ... 读取逻辑
  return tasks.filter(t => t.status !== 'done') // 恢复时也过滤
}
```

这样即使 setTimeout 不执行，下次启动也不会显示已完成的任务。

## 三、架构优化建议

### 3.1 引入统一的 Repository 接口模式

当前每个 repository 有自己的方法签名和错误处理风格：

```ts
// learning.repository.ts - 返回 null 表示未找到
async getUnitDetail(unitId: string): Promise<UnitDetail | null>

// practice.repository.ts - 返回 null 表示未找到
async getTopicDetail(topicId: string): Promise<TopicDetail | null>

// learning-content.repository.ts - 返回 null 表示未找到
async getVocabulary(wordOrId: string): Promise<any | null>
```

**建议：** 统一为 Result 模式（不抛异常）：

```ts
type Result<T> = { ok: true; data: T } | { ok: false; error: string; code?: string }

// 各 repository 统一返回 Result<T>
async getUnitDetail(unitId: string): Promise<Result<UnitDetail>>
```

### 3.2 抽离 SyncEngine 类

当前 `offlineSyncService` 是一个单例对象，包含 `flush()`、`pull()`、`sync()` 三个方法。随着同步逻辑复杂化，建议抽离为独立的 `SyncEngine` 类：

```ts
class SyncEngine {
  constructor(
    private outbox: SyncOutbox,
    private api: SyncApi,
    private stores: SyncStoreRegistry,  // 注册所有需要同步的本地 store
  ) {}

  async push(): Promise<SyncPushResult>
  async pull(): Promise<SyncPullResult>
  async fullSync(): Promise<SyncFullResult>
}
```

### 3.3 学习包安装器重构

将 `learning-pack.service.ts` 的 900+ 行拆分为：

```
lib/offline/
├── learning-pack.service.ts       # 对外 API：installUnit, uninstall, listInstalled
├── pack-installer/
│   ├── zip-reader.ts              # zip 解析、manifest/checksums 读取
│   ├── content-persister.ts       # SQLite 内容写入（topics, ink, 索引）
│   ├── asset-extractor.ts         # 资源提取、SHA256 校验、文件写入
│   └── install-orchestrator.ts    # 编排上述步骤 + 进度报告 + 回滚
```

## 四、数据流统一方案

### 4.1 目标架构

```
用户操作（UI）
    │
    ▼
┌─────────────────────────────────────────────┐
│              Store (Zustand)                 │
│  只做 UI 状态管理，不直接调 API               │
└──────────────────┬──────────────────────────┘
                   │
                   ▼
┌─────────────────────────────────────────────┐
│            Command / Service Layer           │
│  每个用户操作对应一个 Command                │
│  Command 做：① 写本地 SQLite  ② 入队 outbox  │
│            ③ 如果在线，触发 flush（异步）      │
└──────────────────┬──────────────────────────┘
                   │
                   ▼
┌─────────────────────────────────────────────┐
│              Outbox + SyncEngine             │
```

## 六、边界问题汇总

| 边界场景 | 当前处理 | 问题 |
|----------|----------|------|
| App 被杀死（安装中） | 下次启动后恢复 paused 状态，但 SQLite 可能残留半成品 | 无回滚清理 |
| App 被杀死（同步中） | outbox 保留 pending 项，下次启动重试 | ✅ 合理 |
| 网络在安装中途断开 | `AbortError` 被捕获，任务标记 error | ⚠️ 残留数据不清理 |
| 网络在同步中途断开 | 单个 item 失败标记 `failed`，下次重试 | ✅ 合理 |
| 存储空间不足 | `Filesystem.writeFile` 抛异常，错误信息透传 | ⚠️ 没有预检查 |
| 多个包同时安装 | `MAX_CONCURRENT_DOWNLOADS = 2` | ✅ 合理 |
| 同一包重复安装 | `enqueueDownloadTask` 会替换旧任务 | ⚠️ 旧任务的 AbortController 未清理 |
| 登录态过期 | Axios 拦截器跳转登录页 | ⚠️ outbox 中的项会不断重试失败 |
| SQLite 不可用 | `initBackend()` 抛异常 | ⚠️ 上层调用没有统一降级 |
| 从安装中恢复（上次安装被中断） | 检查 `status: 'installing'` 的包... | ❌ 没有这个检查 |

### 需要新增的边界处理

1. **安装前检查磁盘空间**（至少预检 zip 大小的 3 倍）
2. **启动时清理 `status: 'installing'` 且超时的包**（安装开始超过 30 分钟未完成 → 清理并标记 failed）
3. **登录态过期时暂停 outbox 同步**（避免大量 401 错误和无效重试）

## 七、总结

整体来看，当前代码的**架构思路是正确的**——离线优先、outbox 模式、SQLite 本地存储、zip 学习包——这些都是合理的设计选择。主要问题集中在：

1. **数据流不够统一**（两套同步路径、outbox 只覆盖部分数据类型）
2. **关键方法过长**（installUnitFromZip 450行、replayItem 200行）
3. **错误边界处理不完整**（安装失败无回滚、登录过期后 outbox 无效重试）
4. **后端 pull cursor 有数据丢失风险**（这是唯一可能导致用户数据丢失的 bug）

建议按 Phase 1 → Phase 2 → Phase 3 的顺序逐步优化，先修正确性 bug，再做结构重构。
